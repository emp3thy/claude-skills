# Survey: existing tools, agents and skills that detect or fix documentation drift

Research note 03 for the `document-drift` skill design. Date: 2026-10-09.

## Scope and method

This note surveys four families of prior art for a Claude Code skill that scans a repository, finds markdown docs (README.md and other `.md` files, excluding superpowers plan and spec folders), compares them against the code, flags stale docs or docs that describe code that no longer exists, and then fixes them under human review. The families are: (1) agent skills, slash commands and rules for Claude Code and similar harnesses; (2) commercial AI documentation products; (3) deterministic CI tools; (4) research prototypes with code. For each artefact the questions were the same: what it scans, which signals it uses, how it splits deterministic work from LLM work, whether it fixes, how fixes are gated, what the output looks like, and what guardrails exist against false positives or hallucinated rewrites.

Method. GitHub code search through the `gh` CLI located SKILL.md and `.claude/commands/*.md` files (queries such as `"documentation drift" filename:SKILL.md`, which returned 2,840 hits before the shared API rate limit was exhausted). Candidate files were pulled raw through the GitHub contents API or raw.githubusercontent.com and read in full. Product documentation, arXiv abstracts and HTML papers, and tool READMEs were fetched with WebFetch. Twenty WebSearch calls were used. Where only a registry page, a README mention or a search snippet was available, the artefact is marked "snippet" rather than "fetched" and only features with visible evidence are described. Reddit and web.archive.org were not attempted. GitHub issue search pages were not reachable, so the "complaints" section in the synthesis relies on vendor posts, paper failure analyses and skill authors' own guardrail text rather than on issue threads.

Evidence levels used in the tables: **fetched** means the artefact itself (SKILL.md, command file, README, docs page or paper) was read; **snippet** means only a registry summary, a parent README mention or a search result was available.

### Notes per artefact

**mongodb/docs docs-drift.** This is the most carefully engineered skill found. It separates five stages and says which are scripted: extraction of the documented surface from the rendered doc AST (so content pulled in through includes is never reported missing), agent extraction of the source surface into a fixed JSON schema, a deterministic `compare_surfaces.py` diff that emits a candidate for every mismatch "with no curation or early stop, so recall does not vary run to run", agent triage of the complete candidate list into Confirmed, Tracked, Upcoming, Intentional or Needs-eng-confirmation, and a scoring script. The skill never edits docs; it drafts held tickets for Confirmed findings and files them only on explicit approval. Three guardrails stand out: a per-docset manifest with `intent_markers` (source comments such as `// internal` that mean "do not document") and a `calibrated` flag that, when false, biases findings toward "needs confirmation"; a rule that hedged value lists ("such as") are never reported as missing values; and a pinned answer key used as a regression baseline, including two known false positives that must not reappear. The instruction "if a real mismatch class is being missed, fix `compare_surfaces.py`, not by adding ad-hoc agent judgment" is the clearest statement in the survey of where the deterministic / LLM boundary should sit.

**github/awesome-copilot docs-sync-audit.** A read-only audit skill shipped with a standard-library Python script. The script's docstring is a design statement: "Only checks claims that have a definite answer": documented `npm run` / `make` / script commands against the ones that exist, relative markdown links against the filesystem, env var names in both directions between docs and code, and a doc untouched far longer (120 days) than the code it describes. Backticked path checking is opt-in because "most such references are ambiguous ... and reporting them buries the findings that are unambiguous". It also flags a documented setting that is read only inside a module nothing imports. The SKILL.md adds an evidence standard worth copying verbatim: the cited line must literally contain the named thing, any count must appear next to the command that produced it, and absence claims require checking every plausible location. Full-repo audits must list "Surveyed But Not Deeply Inspected" rather than present a shallow sweep as coverage. The fix path is a separate workflow that runs only when the user asks.

**arkhe doc-freshness.** A detection-only skill with a scanner script for links, version references, and git-based staleness, plus agent-driven checks for symbol references and cross-document contradictions. Docs are auto-classified into Basic (every `.md`) and Deep (frontmatter with `last_updated` or `version`) tiers. Its severity table treats "doc stale more than 30 days" as a WARNING, which is a date heuristic the synthesis argues against as a verdict but is fine as a prioritiser. The `onboard` mode proposes tracking frontmatter and applies it only with `--apply`. The registry copy (majiayu000) is an older snapshot of the same skill.

**confluentinc docs-drift.** A project-specific recipe, but the structure generalises: presence diff (schema map vs doc filenames), attribute diff (schema fields vs the doc's attribute table), regeneration of the generator output into a scratch directory as a second opinion with the explicit instruction to diff only the schema-derived sections because hand-written examples "will differ by construction", validation of example blocks with the real toolchain, and fuzzy matching with edit distance 1 to 2 to catch typos that do not collide with a real name. It is read-only unless asked and shows the diff before and after any edit.

**vectorlint doc-drift.** Designed to run on a PR diff in CI. It is pure LLM but disciplined: phase 1 extracts user-visible behavioural changes and discards whitespace, test-only and refactor noise; phase 2 searches docs with exact names, concept variants and feature-area terms and refuses to conclude "no docs" until further searches stop surfacing new files; phase 3 asks a single question per (change, doc section) pair: does the change invalidate a claim in this section. Phase 4 uses a separate criteria file to decide whether an undocumented change is user-facing; internal changes are dropped entirely. Even the no-findings case must explain why the change does not invalidate docs.

**sentry-rust docs-review.** A narrow review skill with two checks (missed update, inaccurate new docs) and a longer list of what not to report (style, missing examples, private items, speculative needs). It knows crate READMEs are generated from rustdoc and reports a stale generated README as a miss. Findings must anchor to a changed line and carry a `verification` trace. It instructs the lower severity "when the mismatch depends on unproven assumptions".

**qwen-code docs-audit-and-refresh.** A fix-capable skill with no explicit human gate. Its restraint rules compensate: prove a gap with repository evidence before editing, edit existing pages first, remove dead text instead of layering warnings, and a validation pass that greps `docs/` for old terminology and checks neighbouring pages for conflicting guidance. It also lists a concrete secondary consumer (a bundled skill with a hard-coded table of doc paths) that must be updated when pages move, which is a reminder that docs reference docs.

**acedergren doc-sync.** Report-only by default, `fix` to apply and commit. Its drift taxonomy with a false-positive-risk column (structural drift low, path rot low, count drift medium, roadmap lag high) is a compact design input. The rule "never fix docs for a section you didn't audit, partial fixes create false confidence" and the git query `git log --since="$(git log -1 --format=%ai docs/SECURITY.md)" -- src/` (commits to source since the doc was last touched) are both reusable.

**laurigates docs-sync.** Catalog synchronisation: counts and tables of skills, commands and agents in CLAUDE.md and README. The detection is deterministic (frontmatter parsing, count regexes such as `**N skills**`) and the only judgement is categorising new entries, with "Uncategorized" as the fallback for human review. `--dry-run` is the gate.

**claude-autopilot docs-sync and docs-fix.** The cleanest deterministic / fix separation in the family. Detection is five grep-level rules with no LLM, writing `drift-candidates.json` with warn-only exit codes and a `.drift-ignore` file. The fix skill converts candidates into either a unified-diff `.patch` (for rules whose fix is mechanical, such as appending a filename to `.dist-include`) or a `.suggestion.md` review template, and refuses to apply anything automatically: each apply runs under `git stash push -u`, pre-validates with `git apply --check`, rolls back on failure, refuses manual-type patches without `--force-manual`, and is forbidden in CI or pre-commit. It also defines bidirectional ownership anchors (`# CODE-REF:` in code, `<!-- CODE-OWNED-BY: -->` in docs) and a fallback `docs-ownership.yaml`.

**aiwg doc-sync.** Notable for context-budget discipline: scope from `git status` and changed files first, ask before expanding to the whole repo, bound each auditor to 10 findings and 600 words, select only the doc "lanes" implicated by changed files. It applies "high-confidence fixes only" and lists human-review items separately.

**piper-plus sync-docs.** Seven parallel Explore agents each audit one doc surface and return proposed markdown diffs; a canonical `release-versions.toml` is the single source of truth for version numbers so version drift is checked by prefix match rather than guessed. Phase 4 is explicit user confirmation before auto-apply.

**dexto /update-docs and jMerta docs-sync.** Both are branch-diff driven. dexto produces a prioritised checklist and waits for the user to choose which items to implement. jMerta's skill identifies "the source of truth for each claim" (code, schema, generated spec, config), edits generated docs only through their generator, and reports docs that remain "intentionally unchanged".

**harness-engineering detect-doc-drift, awesome-slash sync-docs, codocia, docguard.** These four wrap a CLI around the agent. codocia binds each docs page to code globs via `covers:` frontmatter and snapshots content hashes; its check reports stale pages, broken covers, deleted covered files and changed code with no covering page, and its README states the limit plainly: a passing check proves the snapshot is current, not that the prose is right. docguard marks `source=code` regions that a deterministic `sync --write` owns and the agent may not hand-edit, and maps change types to doc sections with a fixed table. harness-engineering classifies findings into renamed, undocumented, deleted, behaviour-changed and moved, caps triage at 30 findings, and lists rationalisations to reject. awesome-slash separates "safe" auto-fixes (version numbers) from review-required ones (removed exports).

**Anthropic and marketplace coverage.** No official Anthropic skill or plugin for documentation drift was found: a code search of anthropics/claude-code plugins for "docs" returned only the plugin-dev skills, and anthropics/skills returned only claude-api material. The registry sites (openskillindex, skills.sh, claudskills, skillselion) index the community skills above; none adds anything beyond the SKILL.md content.

### Notes per artefact

**Swimm.** Swimm is the reference design for deterministic coupling. A doc embeds code snippets, "smart tokens" (identifiers) and paths; on each PR the GitHub app re-verifies every coupled element against the new source. Routine changes such as renames, moves and replaced values are auto-synced and presented for approval with an "Approve Auto-sync" button (or committed automatically if the repo opts in); changes "impactful enough that Swimm oversight is needed" fail the Verify check and mark the element Outdated, at which point a human must replace or delete the element and save. The feature page is explicit that detection is about coupled elements, not prose: Swimm never rewrites a sentence. Two operational details transfer directly: the Verify check can be restricted to files changed in the PR so a repo with pre-existing drift can still adopt it, and comments can be muted during busy periods. The cost is that every claim to be tracked must be coupled by hand in Swimm's editor, which is the reason it is not a drop-in for ordinary markdown.

**Mintlify.** Mintlify's agent is a general writing agent with a code-change trigger: when a PR merges into a connected repo the agent clones the repos, reads the diff, and drafts updates to the matching pages, opening a PR by default and pushing directly only when the "Review process" setting allows it (branch protection overrides that). Scheduled automations run audits for broken links, stale code examples and pages mentioning deprecated features. The drift article recommends triggering on merged PRs rather than pushes, tracking user-facing surfaces (endpoints, parameters, flags, config, response shapes) and skipping internal refactors. The only validation the agent runs is the Mintlify CLI build; accuracy is left to the reviewer, and the agent cites the originating commit or PR so the reviewer can trace the draft.

**ReadMe AI Writer.** The product watches PRs, proposes a draft on a review branch inside ReadMe, and comments on the PR with a preview; public docs are never changed directly. ReadMe's two articles are the best available statement of the noise problem. High-confidence triggers are enumerated (endpoint or parameter added, removed or renamed; documented default changed; install command, env var or setup dependency changed; behaviour described in a guide changed). Cases to stay silent on are also enumerated (internal refactors, tests, build scripts, comments, undocumented code, dependency bumps not in setup docs, diffs too small to judge). Calibration is measured by comment rate across PRs and the conversion rate of comments into merged doc changes: 10 percent of PRs with 90 percent conversion is healthy, 80 percent of PRs means "the signal is gone". The advice is to start strict and loosen as trust builds, and the closing line is "The work is the filtering".

**CodeRabbit docstrings.** A docstring generator rather than a drift detector, but its delivery pattern is worth noting: ast-grep finds functions in the PR's changes that lack docstrings or have incomplete ones, the LLM infers the existing docstring style, and the result is committed to a new branch with a PR opened against the original PR so the author reviews it inside their own change. It "preserves existing docstrings", which is the one guardrail against rewriting what already exists.

**Docverity.** A local CLI that matches the target skill's shape most closely. It splits a free, deterministic reference checker (files, CLI flags, env vars, symbols that no longer exist anywhere in the source) from an LLM claim verifier that runs only when an Anthropic key, the `claude` CLI or MCP sampling is available. Coverage runs in reverse (surface the docs never mention) and uses git history to flag surface added after the docs last changed. An LLM adjudication step filters illustrative examples and "documented as removed" cases. The check never edits; `suggest --write` appends drafts between replaceable markers without overwriting text; in GitHub Actions findings appear as inline annotations on changed PR lines; `--fail-confidence` defaults to 0.7. This is a registry summary, not the README itself, so option names should be re-verified before citing them in a design.

**Doc Detective.** Docs-as-tests: steps written into the markdown (or a JSON spec) are executed against the live product in a browser or against API endpoints, and each step reports PASS or FAIL as JSON. It proves what a step says, nothing more, and it needs a running product. It is the strongest possible signal for procedural docs and irrelevant for architectural prose.

**DeepWiki, Fern, DeepDocs and the generators.** DeepWiki regenerates a whole wiki from the repo at a chosen effort level; the documentation describes regeneration as user-initiated after config changes and gives no refresh schedule, and it does not touch repository markdown. Fern regenerates API reference from the spec in CI and ships a workflow that stamps `last-updated` on any MDX touched in a PR, with a labelled opt-out; the workflow does not verify that the change was substantive. DeepDocs' public material is marketing only. Tessl's "sync-docs" is a community registry skill that maps changed paths against a doc review table in AGENTS.md and patches stale prose in the same change; Tessl Agent's "Docs stay in sync automatically" claim has no documented mechanism. Driver AI, Bito, Cody, Documatic and Scribe generate or search documentation and do not claim drift detection.

### Notes per artefact

**Link checkers (lychee, markdown-link-check, remark-validate-links).** All three prove that a link resolves and nothing about whether the destination still supports the sentence around it. lychee is the most complete (fragments, text fragments, mail, offline cache, per-host rate limits, JSON output) and ships as a GitHub Action; markdown-link-check's `replacementPatterns` with `{{BASEURL}}` handle repos whose root-relative links only work on a hosting platform; remark-validate-links is offline and git-aware, which its README credits for fewer false positives. For the target skill, the relevant subset is relative links and heading anchors, which are fully decidable without network access.

**Linters (markdownlint, Vale).** markdownlint is hygiene only. Vale is a prose linter with user-supplied rules; its one drift-relevant use is a terminology deny-list of retired product, module or flag names, which turns "the docs still say the old name" into a deterministic check once a human has written the list.

**Executable examples (pytest doctest, Sybil, rustdoc, mdbook test, Doc Detective).** These prove that an example runs and produces the expected result against the current code, which is the strongest mechanical evidence available for a documentation claim. Their limits are consistent: only fenced or `>>>` examples are checked; `ignore` or `no_run` blocks are unchecked; a passing example with weak assertions proves little; and surrounding prose is never evaluated. rustdoc's attribute vocabulary (`ignore`, `no_run`, `should_panic`, `compile_fail`) is a good model for how a doc author declares the intent of an example so a checker does not misclassify it.

**Embedders and generators (embedme, mdsh, cog, cargo-rdme, terraform-docs, git-cliff, readme-md-generator).** These eliminate one class of drift by making a region of the markdown derived from code or command output, and each has a CI mode that fails when the committed region differs from the regenerated one (`embedme --verify`, `mdsh --frozen`, `cog --check`, terraform-docs with pre-commit). cog's `-c` checksum additionally detects hand edits inside generated output. The shared limitation is that they cover only marked regions; prose outside the markers is untouched and still drifts. readme-md-generator is a one-shot scaffolder with no later verification. The lesson for a drift skill is that marked regions should be recognised and routed to their generator rather than edited by the LLM, which is also what the awesome-copilot, jMerta and docguard skills instruct.

**Reference resolution and API diff (Sphinx nitpicky, oasdiff, openapi-diff, typedoc coverage).** Sphinx `nitpicky` turns every unresolved cross-reference into a warning, with `nitpick_ignore_regex` for intentional exceptions, which is the same "symbol referenced in docs must exist" check the drift skill needs for markdown. oasdiff and openapi-diff compare two spec versions and classify changes; oasdiff's two tiers (ERR for definite breaking changes, WARN for "potential breaking changes developers should be aware of but cannot be confirmed programmatically") is a useful precedent for separating decidable findings from leads. Neither tool checks that the implementation matches the spec. typedoc-plugin-coverage measures the reverse direction (undocumented surface) and respects a `requiredToBeDocumented` option so the number reflects the policy, not every symbol.

**Repository-level conventions (Ma'at, DOCER, codocia).** Three tools make the doc-to-code relationship explicit so that staleness becomes decidable. Ma'at has docs declare `related_code` in front matter and fails CI on staleness, link errors and generated-file drift, while preserving hand-written AGENTS.md prose by updating only a managed block. codocia (family 1) uses `covers:` globs and content hashes. DOCER needs no declaration: it extracts code element references from README and wiki text with regular expressions, compares the repository at the commit when the doc was last updated against the current revision, and flags a reference that existed then and is gone now. DOCER's authors list the false positives this produces (changelogs that mention deleted elements, elements removed from code whose functionality remains, flags still relevant to users) and offer a `.DOCER_exclude` file. The two-snapshot idea is the key insight: a doc that mentioned a symbol which never existed is a different, lower-confidence case than a doc that mentioned a symbol which existed when the doc was written and has since been deleted.

**Date stamps (Fern last-updated workflow, arkhe and awesome-copilot staleness).** Stamping a date on touched files records provenance, nothing more; Fern's own workflow stamps whitespace-only edits. Comparing a doc's last commit to the last commit on the code it describes (awesome-copilot's 120-day rule, arkhe's 30-day WARNING) is a prioritiser: it says where to look first, not what is wrong, and it breaks on shallow clones.

### Notes per artefact

**DOCER.** The closest research match to the target skill because it works on repository markdown rather than docstrings. It is wholly deterministic: regular expressions pull code element references out of README and wiki pages, the tool counts occurrences in the repository as it was when the documentation was last updated and in the current revision, and anything present then and absent now is flagged. The GitHub Action checks out full history, runs the analysis on `pull_request`, and posts a comment listing potentially outdated references, with `.DOCER_exclude` for suppressions. The earlier study found 28.9 percent of the top 1,000 GitHub projects had at least one outdated reference. The paper does not report precision or recall and instead lists false-positive classes from issues it filed: changelog entries that mention deleted elements by design, elements removed from code whose functionality remains, and user-facing flags that no longer appear in source. The regexes "have not been validated across all programming languages".

**"Does My README File Need To Be Updated?"** (Gao, Lin, Treude, Gay, Zahedi, 2026). An LLM pipeline that, given a PR, decides whether the README needs an update, locates up to five README sections, and justifies each with the triggering event; it never edits. Inputs are PR title, description, commit messages, changed file names and patches, and the pre-update README split into paragraph-level sections. The design is a sequence of narrow components: a high-recall relevance gate, a context-sufficiency check, hybrid retrieval that ranks patches by similarity to both the PR description and README paragraphs, localisation, and a QA reviewer that discards justifications that are "Overly Generic" or "Hallucinated"; in the agentic variant those two verdicts respectively widen or narrow retrieval. Evaluated on 25,511 PRs from 714 repositories with Llama-3.3-70B, Qwen-3-32B and Gemma-3-27B at temperature 0, the best configuration reaches entry recall 0.52 and specificity 0.99, but only 28.7 percent user-facing accuracy once the real 1:99 prevalence of README-updating PRs is simulated. A retrospective found 21.5 percent of flagged-but-unupdated PRs were genuinely overlooked updates, and a maintainer confirmed six of eight recommendations. Failure analysis attributes roughly a third of misses to context deficit (vague PR descriptions, missing project knowledge), about 40 percent to semantically irrelevant noise (cosmetic edits, tangled PRs, wrong ground truth), and about a quarter to structural ambiguity (several valid insertion points, header-level predictions). The paper's argument for surgical recommendations over regeneration is that regenerating a README "risks style drift and the incorporation of hallucinated content" and imposes a far higher review burden.

**READU** (Baek, Krampf, Pradel, 2026). Commit-triggered README bug detection and repair. A high-recall commit filter feeds parallel internal checkers (docs against repository facts) and external checkers (docs against outside facts such as dependencies); an alert judge removes false positives; a patch is synthesised. On 6,000 commits from six repositories including Linux and Spring Boot it reports 244 true positives at 75 percent precision and 217 correct repairs, at under one cent and under a minute per commit, with 66 bugs reported upstream and 44 confirmed. The abstract does not say which models are used or whether code is released. Its "alert judge" is the same role as the mongodb skill's triage stage and Docverity's adjudication.

**CASCADE** (FSE 2026). Detects method-level inconsistency by executing docs: an LLM writes unit tests from the documentation and also writes code from the documentation; an inconsistency is reported only when the original code fails a test that the doc-generated code passes, which filters out wrong tests. The cross-check moves precision from 0.60 to 0.88 at the cost of recall (0.59 to 0.21); on a balanced set it produces 2 false positives, and 31 across 814 consistent methods, but precision drops to 0.39 under a realistic 10/90 split. It found 13 unknown inconsistencies in Java, C# and Rust projects, 10 since fixed. Limitations include low recall by design, non-compiling generated tests, a three-attempt repair loop, and scope limited to method documentation. Code and data are public. The transferable idea is that an executable oracle beats an LLM opinion when one can be constructed.

**DocChecker, CUP family, Panthaplackel, structured diffs.** These are docstring and comment tools, not markdown tools, and are useful mainly as a map of the comment-consistency literature. DocChecker is pip-installable and returns, per function, a consistent / inconsistent label and a recommended docstring that replaces the original only when inconsistent; CASCADE's re-evaluation measured it at precision 0.49 with specificity 0.03 on single-line docs, which is a warning about classifier-style detection applied to prose. CUP (ASE 2020) and its successors HebCUP, HatCUP (ICPC 2022) and CUP2 (OCD detector plus updater) learn to rewrite a method header comment from a code edit; the HatCUP abstract concedes that CUP and HebCUP handle single-token edits and "not good enough for complex ones". Panthaplackel et al. (AAAI 2021) release code for detection, update and jointly trained variants over sequence and AST-diff representations. The SANER 2026 short paper reports that decomposing the diff into replace, delete and add activities over a CodeT5+ backbone beats fine-tuned 7B code LLMs on JITDATA and CCIBENCH. The ICSME 2025 paper shows an LLM given change information produces API docs closer to the human update (METEOR 0.776 vs 0.679 for the stale text) but its abstract does not report over-editing or hallucination rates.

## Synthesis

### (a) The recurring architecture across hybrid tools

Across the skills, products and research prototypes that combine scripts with a model, the same boundary appears again and again, and the better artefacts state it explicitly (mongodb: "the determinism is the point"; awesome-copilot: "only checks claims that have a definite answer"; Docverity: a free reference checker and a paid claim verifier; codocia and docguard: the tool hashes and syncs, the agent judges prose).

Always deterministic:

- Inventory: which files are docs, which are code, which are generated, which are excluded. Every tool reads `git ls-files` or a glob list and a skip-list before anything else.
- Link and anchor resolution for relative links and headings (lychee, remark-validate-links, awesome-copilot, arkhe, Ma'at, confluent).
- Existence of referenced things: file paths, commands and scripts (`npm run x`, `make x`, `./scripts/x`), env var names, CLI flags, exported symbols, resource or attribute names (awesome-copilot script, Docverity, DOCER, confluent, Sphinx nitpicky). Several tools make this two-directional (documented but absent; present but undocumented).
- Generated regions: marker-delimited blocks are regenerated or verified by their generator and never hand-edited (embedme, mdsh, cog, cargo-rdme, terraform-docs, docguard `source=code`, Ma'at managed block).
- Counts and version strings against a canonical source (laurigates count regexes, piper's `release-versions.toml`, arkhe version checks).
- Git temporal signals: doc last-commit vs code last-commit, commits to code since the doc was touched, the doc-time snapshot vs now (DOCER, acedergren, awesome-copilot, Docverity coverage).
- Executable examples where a runner exists (doctest, Sybil, rustdoc, mdbook, Doc Detective, confluent's `terraform validate`).
- The diff step itself when both sides have been reduced to structured data (mongodb `compare_surfaces.py`).

Always LLM:

- Extracting the "documented surface" or claims from prose when there is no renderer AST (vectorlint phase 1, Docverity claim verifier, the README paper's localisation).
- Deciding whether a code change invalidates a specific claim, and whether an undocumented change is user-facing (vectorlint, sentry, ReadMe, Mintlify).
- Triage and adjudication of candidate findings into confirmed, intentional, tracked, upcoming, needs confirmation (mongodb, READU's alert judge, Docverity's adjudication, harness-engineering classification).
- Writing the replacement prose, always presented as a diff, patch, PR or suggestion.

Where tools disagree:

- Whether the LLM may touch the file at all. Detection-only by rule: mongodb, arkhe, awesome-copilot (unless asked), sentry, vectorlint, drift-check, DOCER, the README paper. Fix behind a flag or confirmation: acedergren `fix`, awesome-slash `apply`, laurigates `--dry-run`, aiwg, piper, dexto, autopilot-docs-fix (patch files only). Fix by default with restraint rules: qwen-code, jMerta, docguard. Products converge on "draft on a branch, human merges" (Swimm approve button, Mintlify PR, ReadMe review branch, CodeRabbit PR-against-PR).
- Whether backticked paths and identifiers are checked. awesome-copilot makes it opt-in because the noise buries real findings; arkhe and Docverity check them by default; DOCER checks them and ships an exclude file.
- Whether a date gap is a finding. arkhe reports "stale more than 30 days" as a WARNING; awesome-copilot uses 120 days and calls it a lead; Fern stamps dates without verifying anything.
- How relationships between docs and code are discovered. Declared by the author (Swimm coupling, codocia `covers`, Ma'at `related_code`, autopilot ownership anchors, docguard mapping table, arkhe `.arkhe.yaml`), inferred from the text (DOCER regexes, Docverity, awesome-copilot), or inferred by the model (vectorlint search, README paper retrieval). Declared relationships are precise and costly to maintain; inferred ones are free and noisy.
- Scope. PR-diff-driven tools (vectorlint, sentry, ReadMe, Mintlify, READU, the README paper, dexto, jMerta) only look at docs touched by a change; whole-repo audits (awesome-copilot default, arkhe, confluent, mongodb, DOCER, Docverity) need breadth limits and "not deeply inspected" disclosures.

### (b) Recurring failure modes

Issue threads were not reachable in this session, so the evidence here comes from vendor posts, paper failure analyses, and the guardrails skill authors felt the need to write, which are themselves a record of what went wrong.

- Over-eager rewrites and regeneration. The README paper argues that regenerating a whole file is "destructive, disregarding the existing document's content and style" and risks hallucinated content, and that reviewing a full regeneration costs far more than reviewing targeted edits. The restraint rules in the skills ("edit the minimum", "this is sync, not authoring", "do not rewrite large areas without evidence", "preserve structure, terminology, voice, headings, anchors") exist because agents do the opposite by default. CodeRabbit's "preserves existing docstrings" and Docverity's "appends between replaceable markers without overwriting your text" are product-side versions of the same rule.
- Flagging intentional documentation. Every mature detector carries an intent escape hatch: mongodb's intent markers and Intentional label, DOCER's exclude file and its changelog false-positive class, Docverity's adjudication of "illustrative examples or flags documented as removed", autopilot's `.drift-ignore`, Sphinx `nitpick_ignore_regex`, oasdiff's WARN tier for changes that "cannot be confirmed programmatically", mongodb's rule that hedged lists are never "missing values". Changelogs, migration guides, deprecation notices and tutorials that deliberately show an old API are the canonical false positives.
- Noise and alert fatigue. ReadMe's articles describe the lifecycle (a writer that comments on every PR is ignored, then disabled, then the docs rot again) and propose comment rate and conversion rate as the calibration metrics, starting strict. awesome-copilot turns off path checks by default for the same reason. harness-engineering caps triage at 30 findings. The README paper's 28.7 percent user-facing accuracy at realistic prevalence, READU's 75 percent precision, CASCADE's drop from 0.88 to 0.39 precision under a 10/90 split, and DocChecker's 0.03 specificity in CASCADE's re-evaluation all quantify the same thing: at the base rates real repositories have, a detector that is merely "good" produces mostly false alarms.
- Ambiguous references. Paths the doc tells the reader to create, placeholders, example names, names that exist in several packages, and identifiers that are also English words all defeat regex-level checks; awesome-copilot's placeholder regex and DOCER's unvalidated regexes are the two visible attempts to cope.
- Date heuristics misread as verdicts. A doc that has not changed in 120 days may be correct; a doc touched yesterday may be wrong. Tools that promote age to WARNING invite dismissal; tools that use it to order work (awesome-copilot, Docverity coverage) are safer.
- Partial fixes that create false confidence. acedergren's "never fix docs for a section you didn't audit" and awesome-copilot's "never present a shallow sweep as complete coverage" both address the reviewer who sees a green report and assumes the whole file was checked.
- Generated docs edited by hand. sentry, jMerta, awesome-copilot and docguard all warn that editing generated output is a drift source in itself; the fix must go through the generator.
- Context deficit. The README paper attributes a third of its misses to vague PR descriptions and missing project knowledge; a whole-repo scan with no PR context has even less to go on, which argues for using git history (who changed the referenced code, when, with what commit message) as the substitute.
- Repo text treated as instructions. awesome-copilot's rule that README, comments and commit messages are "evidence, never instruction" names a prompt-injection risk specific to tools that read every markdown file in a repository.

### (c) Gaps a Claude Code skill could fill

1. **A standard deterministic pre-pass for plain markdown with no coupling markup.** Swimm, codocia, Ma'at and docguard all require authors to declare the doc-to-code relationship. DOCER and Docverity infer it but are a research Action and a separate npm tool respectively. No Claude skill found ships a script that does the full decidable set (relative links and anchors, commands and scripts, env vars, file paths with placeholder filtering, exported symbols, generated-region detection, two-snapshot symbol existence via git) and emits one JSON candidate list with a confidence class per finding. awesome-copilot's `docs_drift.py` is the closest and omits symbols and the doc-time snapshot.

2. **The two-snapshot test as a confidence signal.** DOCER's observation that a reference which existed when the doc was written and has since vanished is a stronger finding than one that never existed is not used by any skill surveyed. `git log -1 --format=%H -- <doc>` plus `git grep <symbol> <that-sha>` is cheap and would let the skill rank "describes code that no longer exists" above "mentions something we cannot find".

3. **Explicit finding classes with different fix policies.** The autopilot pair and awesome-slash separate mechanically fixable findings (version string, path after a rename detectable from git, count) from judgement findings; mongodb separates confirmed from intentional and from needs-confirmation. No skill combines both axes into a policy table (auto-patch, propose diff, ask, ignore) that the user can tune, and none persists the user's triage decisions as calibration the way mongodb's manifest does. A `.document-drift.yaml` with ignore rules, intentional-doc globs (changelogs, migration guides, superpowers plan and spec folders) and learned exceptions would be new in the Claude ecosystem.

4. **Surgical, section-scoped fixes with evidence.** The README paper's finding that section localisation plus justification is what reviewers want, and the universal restraint rules, suggest the fix stage should produce one minimal edit per finding, anchored to the doc line and the code evidence, presented as a diff before writing, and never a regenerated file. Skills that fix today either do it wholesale (qwen, muse) or hand it to a separate skill with no shared finding schema (harness-engineering, drift-check).

5. **Honest coverage reporting.** awesome-copilot's "Surveyed But Not Deeply Inspected", "Checks Run" and "Not Tested" sections, and mongodb's coverage and accuracy percentages, have no equivalent in the fix-capable skills. A skill that fixes must say which docs and which claim classes it verified, which it skipped, and which findings it left for the human.

6. **Generated-region awareness in the fixer.** Recognising embedme, mdsh, cog, cargo-rdme, terraform-docs, docguard and Ma'at markers and routing those regions to "run the generator" rather than "edit the text" is cheap and absent from every Claude skill surveyed except docguard's own command.

7. **Calibration metrics for the skill itself.** ReadMe's comment rate and conversion rate, and mongodb's pinned answer key with known false positives, suggest the skill should keep a small regression fixture and report, per run, how many findings the user accepted, which would make noise visible and tunable over time.

8. **PR-diff mode and whole-repo mode as one skill.** The survey splits cleanly into change-driven tools and audit tools. A Claude skill can take either a base ref or nothing, derive scope from changed files when a ref exists (aiwg, jMerta, dexto), and fall back to a bounded breadth-first audit with the awesome-copilot disclosure sections when it does not.
