# Technical debt types as operationalised by detection tools and smell catalogues

Research note for tech-debt-scan v2. Scope: how static-analysis products (SonarQube, CodeScene, Code Climate, Designite, Arcan, tsDetect, duplication, dependency, security and IaC linters) define debt, what symptoms they key on, and how often each symptom actually shows up in real codebases. Prevalence claims are quoted from the sources listed in section 1; anything not fetched in this session is marked as unverified.

## 3. Prevalence ranking rationale

The ordering combines evidence with different units: share of commits carrying a Sonar item (S7), share of releases affected by a manually validated smell (S30), and instances per KLOC (S24, S25). A type ranks higher when it is near-universal in at least two independent datasets and is counted at fine granularity (per statement or file) rather than per project. Magic numbers, duplication, dead code, exception handling and outdated dependencies meet both tests; Long Method and complexity follow because Palomba's 84% of releases and Sonar's 99% of commits agree.

Caveats. Commit-level Apache figures overstate diffuseness: 19 of the top 40 items sit in 90% or more of commits because large commits touch many classes, while the median share of affected classes per commit is at most 15% (S7). The C# densities come from one tool with fixed thresholds, so architecture-smell ranks reflect Designite's heuristics. Palomba's percentages are per release, so density was used to break ties (Long Method at 28 per KLOC dwarfs the rest).

Evidence is thin for dead code (secondary numbers from S46's related work), deprecated API usage (reaction rates, not usage rates), knowledge concentration (one 2016 study), hotspots (a vendor dashboard example), security weaknesses in application code (PyPI is library code and B101 was excluded) and ML debt (no distribution at all). Two often-quoted figures were seen only in search snippets and not fetched: clone rates of 7-24% of code (Roy and Cordy) and "over 90% of SonarQube issues are code smells" (2023 Apache replication). Treat both as unverified.

## 4. Symptom detectability

Legend: (a) static reading of source, (b) git history mining, (c) manifest/config/CI inspection, (d) build, runtime or CI data, (e) human knowledge. "Cheap" means an LLM agent can find it by reading files with pattern matching; "parser" means an AST or metric tool is needed for acceptable precision.

- Magic numbers, duplicated string literals: (a), cheap; regex over literals is close to what Designite and Sonar do. Block duplication: (a), needs token hashing (jscpd, CPD) for coverage.
- Unused imports, commented-out code, TODO/FIXME: (a), cheap. Dead classes and functions: (a) plus reference resolution; a heuristic pass is cheap, knip or vulture for confidence. Files with no inbound imports are cheap at directory scale.
- Outdated dependencies: (c) plus a registry lookup. Manifests, lock files, EOL runtimes and unpinned ranges are readable directly; the newer-or-vulnerable judgement needs network data.
- Exception handling: (a), cheap. Empty catch, catching a base type, throwing a generic type and rethrow without cause are pattern-level.
- Long method, long file, long parameter list, deep nesting: (a), cheap by counting lines, parameters and indentation. Cyclomatic and cognitive complexity: (a), parser preferred; keyword and indentation counts approximate them with more false positives in expression-heavy languages.
- Test smells: (a), cheap; tsDetect's rules are lexical (assertion count without message, Thread.sleep, File instances, control flow inside a test, missing assertions). Flaky tests: (d) to confirm, (a) for leading indicators (sleeps, shared static state, real network calls, unseeded time or randomness), which cover about three quarters of root causes in S36.
- CI and IaC smells: (c), cheap; the most frequent findings are single-line checks (unpinned apt/pip, ADD vs COPY, missing pipefail, missing permissions, missing timeout-minutes, ubuntu-latest, tag-pinned actions).
- Convention violations: (a), cheap but noisy; prefer the repo's own linter config as the source of truth.
- Cyclic dependencies, hub-like coupling, feature concentration, god component: (a) over a dependency graph; approximate at module level from import statements, parser for class level.
- God class, low cohesion, refused bequest, feature envy: (a), parser; cohesion metrics need member-access resolution. Feature envy also has the lowest yield in S30.
- Hotspots, change coupling, knowledge concentration: (b), cheap; churn per file, co-change pairs and author share are a few git commands.
- Security weaknesses: (a) for pattern classes (hard-coded secrets, eval, subprocess with shell=True, string-built SQL); taint classes (XSS, layered injection) need CodeQL or Semgrep dataflow.
- Speculative generality, spaghetti code, deprecated API usage, ML debt: mostly (e). Deprecation needs (c) plus library knowledge; notebook execution-order and pinning checks are (a)/(c) and cheap.

## 5. Open questions and evidence gaps

- No public distribution of SonarQube findings by Clean Code attribute or MQR quality exists; all prevalence figures are by legacy rule key.
- CodeScene thresholds are language-specific and ship as a zip that could not be read; only the config key names and the 8.0/4.0 healthy/alert cut-offs are confirmed. Customer-wide smell prevalence is unpublished beyond the 11% non-healthy share in Code Red.
- Code Climate defaults were verified only through a third-party config; the vendor page redirects.
- Sonar rule titles for the keys in S7 were not fetched; keys are exact, titles are from general knowledge.
- Architecture-smell prevalence rests on one C# study with Designite thresholds; Arcan-based Java figures (Arcelli Fontana, Gnoyke) were located but not fetched.
- Dead-code prevalence has no primary large-scale measurement; the 5-30% range comes from three small studies cited in S46.
- Test-smell prevalence outside Java and per-file numbers for enterprise code are absent; Android open source is the largest dataset found.
- Semgrep, CodeQL and GitHub code-scanning alert distributions are not published at rule level; CWE Top 25 ranks CVEs, not alerts.
- No findings distribution exists for ML or notebook debt beyond reproducibility rates.
- S8 and S9 show weak links between detected debt and faults, so prevalence is not importance. Rank by prevalence for coverage, but weight by impact evidence (Code Red, Palomba change-proneness) when promoting items.
