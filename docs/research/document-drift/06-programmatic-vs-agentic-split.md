# document-drift: where the programmatic/agentic line sits

Synthesis document, written 2026-10-09 from the five research notes in this folder: `01-what-good-looks-like.md` [01], `02-drift-issue-taxonomy.md` [02], `03-survey-existing-tools-and-skills.md` [03], `04-fix-workflows-and-safety.md` [04] and `05-repo-primitives-and-conventions.md` [05]. It answers one question: for a skill that scans a repository's markdown, compares it against the code and then fixes what has drifted, which work is a deterministic script and which work is an LLM agent, and why. Nothing here is decided; `07-brainstorm-brief.md` turns the contested points into questions for the brainstorming session.

## 1. The principle, as three sources state it

This repository already states the rule for its other two skills: "LLM does the judgement, scripts do the determinism" (`docs/architecture.md:22-30`, quoted in [05] section 4). In tech-debt-scan's fifteen-step chain, twelve steps are scripts and exactly three are agents (scout, verifier, note writer); no agent orders the final list, a scout never self-reports confidence and a scout never proposes a fix ([05] section 4).

The seven hybrid tools surveyed in [04] section 6 (Ruff, ESLint, Semgrep Assistant, CodeQL plus Copilot Autofix, Sourcery, Swimm, Amazon Q, Moderne/OpenRewrite) draw the same line independently: the deterministic layer owns detection, finding identity, scoping of what the model sees, application of meaning-preserving edits and post-hoc verification; the model owns judgement calls and prose, and is never the thing that decides whether its own output is applied.

The documentation-specific tools in [03] synthesis (a) converge on the same boundary with one more element: extracting claims from prose when there is no renderer AST is the one detection task that is always LLM.

So the question is not whether to split but where the edges are. The next three sections give the split per pipeline stage, per drift category and per fix, then section 5 lists the places where the evidence does not settle it.

## 2. The split by pipeline stage

| Stage | Layer | What it does | Why there | Evidence |
|---|---|---|---|---|
| Doc inventory and classification | Script | Walk the tree, classify every file (doc, source, test, generated, vendored), apply the exclusion list (superpowers plan and spec folders, CHANGELOG, LICENSE, ADR and RFC folders, `linguist-generated` and `linguist-vendored` attributes, `DO NOT EDIT` headers, `vendor/`, `node_modules`, submodules, template placeholders) | Every surveyed tool does this deterministically; a scan that lets the model decide scope cannot report coverage honestly | [03] synthesis (a); [01] implications 13 and 14; [05] P1 and P2 |
| Reference extraction from markdown | Script | Parse fenced blocks, inline code spans, links, anchors, images, badges, directory trees, tables; emit typed tokens: path, URL, anchor, identifier, command, flag, env var, config key, version string, make or npm script | A markdown AST is available, so there is no need for a model to find the tokens. Precision of the token classifier is the main noise source and must be testable | [03] gap 1; [02] section 4 "reading the table"; [05] P4 limits (two regexes today, no fence or link awareness) |
| Resolution against the repository | Script | For each typed token: does the path exist, does the anchor exist, does the symbol appear in the referenced module's identifier set, does the flag appear in the parser or `--help`, does the key appear in the schema or defaults, does the version match the manifest, does the make or npm script exist | Grounded checks reach 0.9 precision where prose-to-prose LLM judgement sits at 0.6 ([01] section 3). The resolvable token set covers "well over half of drift fixes" in the sample ([02] section 4) | [01] implication 2; [02] DD-01 to DD-06, DD-09, DD-12, DD-16; [05] P5 |
| History and rename lookup | Script | For each unresolved token: `git log --follow`, rename detection, `git log -S` for the replacing name, the two-snapshot test (did the token resolve at the doc's last substantive commit) | The replacement comes from history, not imagination: both published fixers with merged patches derive the fix from the target's history. The two-snapshot test is the single strongest confidence signal and no skill surveyed uses it | [02] implications 2 and 3; [03] gap 2; [05] section 3 (git_history has no rename detection today) |
| Temporal signals | Script | Per doc, per referenced path: has the code changed since the doc's last substantive commit (excluding formatting, bot and link-fix commits); kind of change (signature, rename, declaration raise priority; literal and lambda changes do not) | Cheap and informative for ordering, but only 13 to 20 percent of code changes need a doc update, so lag alone is a lead, not a finding | [01] section 3 tier 3, implications 1, 10 and 20; [03] failure mode "date heuristics misread as verdicts" |
| External link check | Script, optional, network | HTTP status and redirect chain with cache, token, retries and ignore file | Deterministic when it succeeds; transient failures must never count as drift | [01] implication 16; [02] DD-01 |
| Executable examples | Script where a runner exists | Parse or compile fenced blocks; run doctest-style blocks in a sandbox when the repo has a runner; compare printed output | A parse error or an import of a missing module is near-certain drift; a runtime failure may be environmental. Execution is a repo-policy question (see section 5) | [01] implication 12; [02] DD-07 |
| Lead selection and prompt rendering | Script | Choose which documents and paragraphs an agent reads, bundle the diff and the affected paragraph, render prompts to files, cap breadth | Giving the model the diff and the paragraph rather than the whole README and codebase took specificity from 0.70 to 0.99 ([01] implication 5). Scoping the model's context is a deterministic responsibility in every hybrid tool | [01] implication 5; [04] section 6; [05] C-rules on prompt files and argv limits |
| Claim extraction and behaviour judgement | Agent, read-only | For leads the resolvers could not settle: does this paragraph describe behaviour the code no longer has; is this example still what the code does; is this architecture prose still true; is this an under-promise (not drift) or an over-promise or a direct mismatch | The one task that needs reading comprehension. Must be constrained to an enumerated yes/no schema with incompleteness dropped in code, because instruction alone did not stop a 98 percent flag rate | [01] implications 4 and 18; [02] DD-07, DD-08, DD-10, DD-11; [03] synthesis (a) "always LLM" |
| Candidate merge and quote relocation | Script | Re-find every quoted doc line and code line on disk; divert any finding whose quote is absent; fingerprint by rule, path and surrounding text, not by line number | A fabricated citation must never reach the report. Content-based identity is what lets accepted exceptions survive edits | [04] implication 16; [05] P12 and merge_findings precedent |
| Verification of agent findings | Agent, read-only, fresh context | Confirm, downgrade, reject or refer each comprehension finding against the family's questions and traps (planned interface, external interface, generated doc, historical doc) | tech-debt-scan's verifier pattern; a second chain "works like another human in the loop" | [04] implication 10; [05] P16 |
| Classification of each finding into a fix class | Script | Apply the safety ladder (section 4) from the finding's evidence: resolved rename with unique candidate is class A, no candidate is class B, comprehension finding is class C or D, normative or intent doc is class E | The deterministic layer classifies applicability (Ruff's Safe, Unsafe, DisplayOnly); the model never grades its own output | [04] section 2 and implications 1 to 4 |
| Fix text for class A and B | Script | Token replacement from the rename map; deletion of the line, bullet or row with an orphan-sentence check | Every token introduced is traceable to a repository artifact by construction; a deletion cannot hallucinate | [01] implication 7; [04] classes A and B |
| Fix text for class C | Agent, constrained | SEARCH/REPLACE hunk anchored to exactly one match, every changed sentence citing a `path:line` that was in the prompt, length at most twice the original, no new headings, fences or unseen identifiers | LLM comment rewrites are judged correct 55 to 65 percent of the time, acceptable for a proposal, not for an unattended commit | [04] class C and implications 7 to 9 |
| Independent check of class C hunks | Agent, fresh context | "Does the rewritten sentence state anything the cited lines do not support?" Reject on yes | Hallucination control by a second pass, as Semgrep Assistant and DocAgent do | [04] implication 10 |
| Report rendering, status round-trip, parsing | Script | One markdown report with stable finding IDs, class, evidence, proposed hunk and a `status:` the human edits; a parser reads back IDs, never prose | The repository's design.md precedent; git-rebase and Renovate dashboards do the same | [04] implication 14; [05] P8 to P10 |
| Application of approved fixes | Script | Apply hunks in content-identity order, `.tmp` then `os.replace` with `.bak`, one hunk per change, no multipass chaining | Application of meaning-preserving edits is deterministic in every hybrid tool; ESLint applies suggestions as stand-alone changes | [04] implication 5; [05] P27 |
| Post-fix verification | Script | Re-run the resolvers on the edited doc; the finding must go to zero and no new finding may appear; link check on touched links; markdown parses; diff-shape check | Copilot Autofix's internal gate; a fix that does not take the finding to zero is not presented | [04] implication 11 |
| Baseline and re-run classification | Script | NEW, UNCHANGED, moved, edited, RESOLVED against the previous run; honour `<!-- drift-ignore: REASON -->` markers and report markers whose finding no longer fires | Idempotence is a script property | [04] implications 15 and 16; [05] P13 |
| Coverage report | Script | Which docs, which token classes and which claim classes were verified, skipped or not deeply inspected; acceptance per class from the status file | A skill that fixes must say what it did not check | [03] gap 5; [04] implication 20 |

Counting the rows: fourteen stages are scripts, four are agents, and the agent stages are all read-only except the constrained class C fix author, whose output is applied by a script only after a human approves it. That ratio matches tech-debt-scan's twelve to three.

## 3. The split by drift category

The taxonomy in [02] section 4 gives eighteen categories. This table assigns each a detection layer and a fix class from the ladder in [04]. "Resolver" means the script stage in section 2; "agent" means the comprehension stage.

| ID | Category | Detect | Fix class | Note |
|---|---|---|---|---|
| DD-01 | Dead or moved external URL | Resolver (network) | A for redirect rewrite, B for removal of a dead link, D when the referenced thing is gone entirely | Transient failures excluded |
| DD-02 | Broken intra-repo link, anchor or path | Resolver | A when history gives a unique rename, B when deleted with no candidate, D when several candidates | The single most mechanical class; 15-month lags seen in the sample |
| DD-03 | Stale badge or service widget | Resolver | B | Cross-check workflow and branch names |
| DD-04 | CLI flag or subcommand removed or renamed | Resolver against parser or `--help` | A for rename, B for removal, C when semantics changed | Flag extraction is language-specific per parser family; a `--help` diff is the language-agnostic form |
| DD-05 | Config key, env var or default | Resolver against schema or defaults | A, B, C for defaults | Env var reads are grep-able across languages |
| DD-06 | Identifier in prose no longer exists | Resolver (identifier set of the referenced module) plus history | A for unique rename, B for removal, D when ambiguous | Needs the two-snapshot test to separate "gone" from "never existed" |
| DD-07 | Code example wrong | Script parse or run, then agent | C, verified by re-running | Execution policy is an open question |
| DD-08 | Install or setup steps stale | Resolver for script names, targets, files; agent for the procedure | A and B for the mechanical parts, C for procedure, E for platform-support decisions | The largest README category in every source |
| DD-09 | Version or platform string | Resolver against manifest | A | Copy from the manifest; never from prose |
| DD-10 | Feature or behaviour claim | Agent, led by negation and time-anchored words that name a symbol | C with the citing commit as evidence; E when the claim is intent or roadmap | Stale negations are the best hunting ground |
| DD-11 | Architecture or how-it-works prose | Resolver for directory trees and component tables; agent for narrative | C for structural parts, E for rationale | Report only missing or renamed entries, never unlisted ones |
| DD-12 | Enumeration out of sync | Resolver against the registry, directory or enum | B for removals, C for additions | Additions need a description, hence C |
| DD-13 | People or sponsor lists | Not scanned | E at most | Social decision, out of scope by default |
| DD-14 | Whole document obsolete | Resolver ratio (unresolved identifiers over total) plus age | E with a deletion proposal | Deletion of a page is a maintainer decision |
| DD-15 | Status-tracker documents | Resolver for closed issues and passed dates | A for date-passed and issue-closed entries, E otherwise | Only when the repo keeps such files and they are not excluded as historical |
| DD-16 | Naming and terminology drift | Resolver with a rename map | A when 1:1 and documented in history, E when the old name is a legitimate historical reference | Rename map from `git log -S` and changelog |
| DD-17 | Incorrect at birth | Resolver with fuzzy match (edit distance 1 to 3) | A for identifiers, C for wording | Same machinery as DD-06 |
| DD-18 | Doc right, code wrong | Agent, on normative sentences ("must", "guarantees", "always") | E, always | A doc fixer must never "fix" the doc here; route with both sides shown |

Reading down the Detect column: eleven of eighteen categories are resolver-first, four are agent-first, three are mixed. Reading down the Fix column: classes A and B (script-authored, auto-applied under the default policy) cover most of DD-01 to DD-06, DD-09, DD-12, DD-15 and DD-16, which the sample in [02] says is the majority of what maintainers actually fix; class C (agent-authored, per-hunk approval) covers DD-07, DD-08 procedure, DD-10 and DD-11 structure; class E (flag only) covers DD-13, DD-14, DD-18 and every rationale or intent section.

## 4. The fix ladder, restated as a policy table

From [04] "Proposed safety ladder", kept here so the split document is self-contained:

| Class | Name | Who writes the text | Applied by | Default policy | Must pass |
|---|---|---|---|---|---|
| A | Safe | Script (rename map, manifest value) | Script, batched into one commit | Auto-apply, reported | Target exists at HEAD; replaced token appears verbatim; hunk changes only the token; detector goes green; link check on touched links |
| B | Safe-delete | Script (delete line, bullet, row) | Script, one hunk each, listed prominently | Auto-apply | No file, symbol, flag or anchor matches at HEAD including fuzzy rename; remaining text still parses; deletions only |
| C | Unsafe | Agent under constraints | Script, after per-hunk human approval | Proposed, opt-in per hunk | Exact single SEARCH anchor; `path:line` per changed sentence, resolving and present in the prompt; at most twice original length; no new headings, fences or unseen identifiers; second-model check; detector goes green |
| D | Display-only | Agent, shown as a candidate | Never by the tool | Shown, human edits by hand | None applied; dismissal with a reason becomes an inline marker |
| E | Flag-only | Nobody | Never | Reported with both sides | Routed to a human with "doc is right / code is right / both wrong" |

Two policy knobs the user should be able to turn, by analogy with Ruff's `extend-safe-fixes` and `extend-unsafe-fixes`: promote or demote a rule's class, and set which classes auto-apply (the conservative default being none, the Ruff-like default being A and B). Any finding with more than one valid resolution demotes to D automatically. Any mismatch where the code changed within the last N days routes to E as a possible regression ([04] implication 12).

## 5. Where the evidence does not settle the line

These are the places the brainstorming session has to decide. Each is stated with the two sides and the evidence for each.

**5.1 Who discovers the doc-to-code relationship.** Declared relationships (Swimm coupling, codocia `covers`, Ma'at `related_code`, a mapping table in CLAUDE.md) are precise and cost the author maintenance; inferred relationships (token extraction, DOCER regexes, model search) are free and noisy ([03] synthesis (a) "where tools disagree"). The deterministic token extractor gives an inferred map for free; the question is whether the skill also reads a declared map from a config file and whether it writes back the map it inferred so the next run starts with memory (the Dosu CLAUDE.md pattern, [01] implication 17).

**5.2 Whether backticked identifiers are checked by default.** awesome-copilot made it opt-in because the noise buried real findings; arkhe and Docverity check by default; DOCER checks and ships an exclude file ([03] "where tools disagree"). The two-snapshot test is the proposed answer (a token that resolved at the doc's last commit and no longer does is a strong finding; a token that never resolved is a weak lead), but it is untested on this repository's own docs.

**5.3 Whether the agent authors class C text before or after human approval.** tech-debt-scan's note agent writes remediation prose before the human reads the report, so the human approves a concrete diff ([05] section 4, last paragraph). The alternative is to flag first, author only for approved findings, which saves agent cost on findings the human rejects. The acceptance data ([04] section 1: 61 to 92 percent for agent documentation PRs, two-thirds for Autofix) suggests most proposals are accepted, which favours authoring first; the "reviewer abandonment at 38 percent" figure suggests keeping the report short, which favours authoring only what survives verification.

**5.4 Change-aware or whole-repo scope, or both.** PR-diff tools only look at docs touched by a change; whole-repo audits need breadth limits and "not deeply inspected" disclosures ([03] gap 8). JIT detection beat post hoc by 12 F1 points ([01] implication 1). The proposed answer is one skill that takes an optional base ref and derives scope from changed files when given one, otherwise runs a bounded audit ordered by temporal signals; the open question is the default and the breadth cap.

**5.5 Whether fenced code blocks are executed.** Running examples is the most reliable DD-07 signal, but it executes project code, which tech-debt-scan's non-goals forbid ("any tool that executes project code"), and the runner is language-specific ([01] implication 12; [05] section 1). Parse and import-resolve only, run only when the repo already has a doctest-style runner configured, or never run: three positions.

**5.6 Whether date lag is a finding, a warning or only an ordering key.** arkhe reports more than 30 days as WARNING, awesome-copilot uses 120 days as a lead, Fern stamps dates without verifying ([03] "where tools disagree"). The evidence that only 13 to 20 percent of code changes need a doc change ([01] section 3) argues for ordering key only.

**5.7 Whether classes A and B auto-apply by default.** Ruff's precedent and the sample's preference for deletion say yes; this repository's "nothing is fixed automatically" precedent and the exclusion of fixing from tech-debt-scan's goals say no ([05] C18). A middle position: A and B are applied only after the human flips the report's status, like every other class, but are pre-approved in bulk by a single status at the top of the report.

**5.8 What "language-agnostic" means for flag and config resolution.** Path, anchor, link, version and script resolution are language-neutral. Flag resolution against argparse, clap, cobra or commander, and config-key resolution against pydantic, JSON Schema or a struct, are parser-family specific. The repository rule allows one language-aware table ([05] C-rules; `docs/architecture.md` design principles). The language-neutral form is to diff the doc's flags against `--help` output when a command is runnable, and against a union-of-idioms regex over the parser source otherwise; whether that is precise enough is unmeasured.

**5.9 Standalone skill, promotion target, or both.** [05] section 3 gives three shapes: standalone (the brief), promoted from a tech-debt-scan `doc-drift` finding through `evidence.md` (one branch in promote step 7 and a `--from-evidence` flag), and a later feedback edge through the tool registry (blocked today by the tier B cap). Standalone first with the promote seam designed in is the cheapest reading, but it is a decision.

**5.10 Code sharing with tech-debt-scan.** The repository's precedent is copy-and-rename with no shared package, which is itself a drift hazard; a byte-equality test per copied file is the proposed guard ([05] section 7). The set to copy is named there.

## 6. The recommended line, in one list each

Scripts, with pinned commands and pinned output files: inventory and exclusions; markdown parsing and typed token extraction; resolution of every token against tree, manifests, parsers, schemas and registries; history and rename lookup including the two-snapshot test; temporal signals as ordering keys; optional external link check; parse-level checks on fenced blocks; lead selection and prompt rendering to files; quote relocation and fingerprinting; fix-class assignment; class A and B text; hunk application; post-fix re-detection; report rendering and parsing; baseline diff; coverage and acceptance reporting.

Agents, read-only unless stated: comprehension of leads the resolvers could not settle, against an enumerated schema that cannot express incompleteness; verification of comprehension findings in a fresh context; constrained authoring of class C hunks; independent faithfulness check of class C hunks. No agent decides scope, orders the report, classifies its own applicability or applies an edit.

The one place the line is genuinely new relative to tech-debt-scan is the fix stage, and the evidence from Ruff, ESLint, Copilot Autofix and Swimm is consistent: the model may write replacement prose, the script decides whether that prose is applicable and applies it, and a human approves every hunk that a script could not prove.
