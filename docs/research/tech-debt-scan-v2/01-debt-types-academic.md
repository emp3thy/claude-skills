# Technical debt types and symptoms: evidence from the academic literature

Research note for tech-debt-scan v2. Compiled 2026-09-02. Scope: peer-reviewed taxonomies, surveys, and mining studies of technical debt (TD), ranked by how often each type occurs in real software, with the repository-observable symptoms a read-only, LLM-driven scanner could detect.

Sources were located by web search and read either as HTML or as PDF text extracted locally with pypdf. Items marked "abstract only" were read from the arXiv abstract page. ## 3. Prevalence ranking rationale

No single study ranks all types on one scale, so the order above is a judgement across five lenses that measure different things.

**Occurrence in artefacts.** The most direct measures of what sits in repositories are the SATD studies and the smell-mining studies. In code comments, the two largest samples disagree: Maldonado and Shihab's five-project manual study found design debt dominant (42% to 84%), while Bavota and Russo's 159-system sample found code debt first (30%), then defect and requirement (20% each), then design (13%). In issue trackers, code (38.8%), documentation (21.7%), and test (18.4%) dominate (S8). Smell-mining studies show near-saturation for the top code smells (Long Method in 84% of releases, S16) and test smells (82% of test classes, S15). This lens puts code debt first and test and documentation debt high.

**Occurrence reported by practitioners.** InsighTD asked 653 practitioners to classify the TD item from their exemplar project (S3). Design 21.99%, test 19.94%, code 14.66%, architecture 10.70%, documentation 9.09%, requirements 8.80%, then a long tail under 5%. The authors' own conclusion is that "there is no single TD type that stands out". This lens elevates design debt to the top and matches the artefact lens on test, code, and documentation.

**Importance reported by practitioners.** Ernst et al.'s 1,831-response survey found architecture choices to be the most significant source of debt, with roughly nine in ten respondents on older systems agreeing (S4). Architecture debt is therefore ranked above documentation and requirements despite lower occurrence counts, because practitioners consistently identify it as the most costly type. Requirements debt, conversely, shows the weakest association with wasted time (9.0% of variance, S5) and is ranked below its InsighTD share.

**Cost in developer time.** Developers waste on average 23.1% of working time on TD (median 17.13%; replication about 25%; a separate survey estimate of 36%), and the strongest association is with testing issues, followed by code and architecture (S5). This supports placing test debt at rank 3.

**Visible versus invisible debt.** Kruchten's TD landscape (S19) places new features, defects, and low external quality on the visible side and architectural debt, structural debt, code smells, and low internal quality on the mostly invisible side. This is why defect debt and unimplemented features are contested as TD at all (S1 records four studies arguing defects are not TD), and why they are ranked below types that every taxonomy accepts.

**Research attention.** Li et al. counted studies per type: code 25/38, test 15/24, architecture 15/25, design 14/23, documentation 10/19, defect 7/11 (S1). Attention is a poor proxy for prevalence but confirms the same top cluster. Alves et al.'s update notes that from 2015 to 2022 no papers addressed documentation, people, build, service, or usability debt, and that comments and commits displaced code smells as the most-used identification indicator because of 34 SATD papers (S2).

**Where evidence is thin.** Dependency and aging debt (rank 7) has no occurrence figure in the classic taxonomies; the 21%-of-repositories figure (S34) and the security-debt interviews (S26) justify placing it mid-table, and its detectability from manifests argues for keeping it separate. Security debt has interview evidence only; the 42% figure it cites is an industry report and was not verified. Everything from rank 14 down rests on AI-specific mapping studies or single mining studies. Ranks 18 to 20 are placed at the bottom because every lens agrees they are rare (all under 1% in InsighTD).

Legend: (a) static reading of source, (b) git history mining, (c) manifest and config inspection, (d) requires runtime or CI data, (e) requires human knowledge. Strong = a scanner can name concrete instances with high confidence; Partial = it can raise a candidate that needs confirmation; Weak = only indirect hints.

| Data debt | Partial: hard-coded paths, missing schema checks, data-access SATD | Partial | Partial: dataset versions in config | Data profiles need a run | High |
| Model debt | Partial: dead experimental branches, glue code, literal thresholds | Partial | Partial: model registry or absence of it | Skew and staleness need serving data | High |
| Configuration debt | Partial: config size, duplication across environments | Partial: config churn | Strong: sprawl, untested or unversioned config | Not needed | Medium |
| LLM-specific debt | Strong: prompt literals, output parsing, model name pinning, hallucinated imports | Strong: duplication and churn spikes, provenance gaps | Partial: SDK and model versions | Nondeterminism needs runs | Medium |
| Versioning debt | Partial: vendored forks, copy-paste variants | Strong: long-lived divergent branches | Weak | Not needed | Medium |
| Process and people debt | Weak | Partial: ownership concentration, review participation | Not applicable | Not needed | High |
| Other rare types | Weak | Weak | Weak | Not needed | High |

Practical consequence: a read-only scanner has strong evidence for ranks 1, 3, 4 (structural sub-types), 5, 9, 11, and 17, manifest-driven evidence for 7 and 10, and can only nominate candidates for 2, 6, 8, and 12 to 16. Architecture debt splits: dependency-graph smells are cheap to compute, but the ATD items practitioners find most costly (framework choices, neglected architecture maintenance) leave few static traces, and their symptoms (recurrent patches, functionality in the wrong component, inconsistent copies of data) need domain context to interpret (S18).

## 5. Open questions and evidence gaps

1. **Design versus code debt ordering depends on the sample.** The five-project manual study places design debt first; the 159-system study and the issue-tracker study place code debt first. Classification boundaries between "code" and "design" SATD are inconsistent across papers, so the scanner should treat them as one family with sub-labels rather than compete on the split.
2. **No study ranks all 15 to 20 types on a single occurrence scale in a broad corpus.** InsighTD is the closest, but it counts one exemplar item per respondent, not items per repository.
3. **Practitioner importance and measured occurrence disagree on architecture debt.** It is first for importance (S4), fourth for occurrence (S3), and sixth in issue trackers (S8). The wasted-time association for architecture is third after test and code (S5). A scanner that ranks by occurrence alone will under-weight it.
4. **Dependency, security, and CI/CD debt lack occurrence figures comparable to the classic types.** The available numbers (21% of repos with aging SATD, 42% of applications from an unverified industry report, 67.7% of pipelines with absent feedback) come from different denominators.
5. **SATD-based prevalence undercounts silent debt.** Only 2.4% to 31% of files carry SATD (Potdar and Shihab 2014, via S6) and 0.3% of comments on average (S7). Code and test smells are far more diffuse than their SATD counterparts, so keyword detection should supplement, not lead. Flaky-test prevalence is likewise unmeasurable without CI history; the 4.56% figure is Google-internal and cited second-hand (S20).
6. **LLM-era evidence is young and largely grey.** The strongest claims about AI-generated code (duplication outpacing reuse, 30% more static warnings, 40% remediation) come from vendor or blog sources aggregated in S25 and were not verified here. A "93% of GitHub survey respondents" documentation figure seen only in search snippets is likewise not used.
7. **Removal and survival data exist mainly for SATD and test smells.** Comment SATD is fixed in about 57% of cases after more than 1,000 commits (S7); test smells in 2.34% (S15). Comparable survival data for architecture and dependency debt would improve any interest estimate.
