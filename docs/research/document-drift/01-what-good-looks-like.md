# Document drift: what a good detect-and-fix tool looks like

Research note for the `document-drift` Claude Code skill. Written 2026-10-09.

## Scope and method

This note answers five questions about documentation drift (markdown docs that no longer match the code they describe): how the literature defines and classifies it, what mature engineering organisations do to keep docs honest, which signals are usable to decide a doc has drifted, what a good fix looks like, and where false positives come from. The method was 23 web searches and roughly 45 page fetches over arXiv abstract and HTML pages, ar5iv mirrors, conference pages, vendor documentation and practitioner blogs. One PDF (Wen et al. 2019) was downloaded and text-extracted locally because the fetch tool could not read it inline. Reddit was not attempted. `github.com` returned HTTP 403 to the fetch tool, so GitHub-hosted READMEs (lychee, stale-cli, Doc Detective) were read through mirrors, npm or docs sites where possible, otherwise they are marked snippet-only. `socket.dev` and `npmjs.com` also returned 403 for stale-cli, so that tool is snippet-only. Every source in the table at the end is marked as fetched (the page was read) or snippet (only a search result summary was seen). Precision and recall figures are quoted only where the paper itself reports them.

## 1. Definitions and taxonomies in the academic literature

### Terminology

The literature uses several overlapping terms for the same family of problems. "Code-comment inconsistency" (CCI) is the oldest and most studied, and refers to a natural-language comment that no longer describes the method or block it is attached to. "Outdated comment" or "obsolete comment" is the same thing viewed as a temporal event. "Documentation smell" is a different idea: a presentation defect that does not make a doc wrong but makes it hard to use. "Documentation issue" taxonomies cover the whole space including correctness, completeness and up-to-dateness. Recent LLM-era papers prefer "code-documentation inconsistency" and distinguish incorrectness from incompleteness. README-specific work is sparse and recent.

### Foundational empirical work on co-evolution

Wen, Nagy, Bavota and Lanza (ICPC 2019) mined 1.3 billion AST-level changes from the full history of 1,500 Java systems and manually analysed 500 commits in which developers fixed comments (fetched, PDF extracted). Their key quantitative finding is that only 13% to 20% of code changes trigger an update to the related class or method comment, which they explicitly say "does not imply that in the remaining about 80% of cases code-comment inconsistencies are introduced", because many code changes do not require a comment change. They confirm Fluri et al. 2007, who found that 23%, 52% and 43% of comment changes in three systems were triggered by code changes, and that 97% of those comment changes landed in the same revision as the code change. The change types least likely to trigger comment updates were Array, Lambda, Iteration, Literal, Method Invocation and Name (rename refactorings), and they document real inconsistencies caused by renames. Variable Declaration, Selection, Method Signature and Constructor changes were most likely to trigger comment updates. Their taxonomy of comment-related fixes has six root categories: Application Logic, Code Design/Quality, Maintenance, Formatting/Readability, Copyright/License and Others, with 69 change types of which 25 are relevant to inconsistency. Two details matter for a README tool: they found "invalid or outdated references in comments" to other code elements and bug reports as a distinct inconsistency type, and they found copyright headers that stayed wrong for years after a licence change.

Aghajani et al. (ICSE 2019, "Software Documentation Issues Unveiled") mined 878 documentation-related artifacts from mailing lists, Stack Overflow, issues and pull requests (snippet, plus a fetched secondary summary). Their taxonomy has four top-level dimensions: Information Content (What), with sub-categories correctness, completeness and up-to-dateness; Information Content (How), with maintainability, readability, organisation and usefulness; Process-related; and Tool-related. The 2020 follow-up validated the taxonomy with 146 practitioners (snippet). For a drift tool, the What dimension is the target: a drifted doc is one with a correctness or up-to-dateness issue, and incompleteness is a different, lower-priority problem.

Rani et al. (JSS 2023, "A Decade of Code Comment Quality Assessment") reviewed 47 papers from 2010 to 2020 (snippet). They report there is no single definition of comment quality, that 21 quality attributes appear in the literature but studies concentrate on four, that consistency between comment and code dominates the research, that most work targets Java, and that researchers mostly rely on manual assessment and specific heuristics rather than automated checks.

### Documentation smells

Khan, Khondaker, Uddin and Iqbal (SANER 2021) catalogued five API documentation smells from the literature: Bloated (verbose, hard to follow and update), Excess Structural Information (too many class or package names), Tangled (mixes in unrelated information), Fragmented (information scattered across pages via references) and Lazy (adds nothing beyond the signature) (fetched via ar5iv). On a benchmark of 1,000 manually labelled Java documentation units, their rule-based detectors reached F1 of 0.90 (Bloated), 0.95 (Lazy), 0.42 (Excess Structural), 0.41 (Tangled) and 0.47 (Fragmented); BERT reached 0.93, 0.97, 0.76, 0.83 and 0.75 respectively. In their survey of 21 developers, 95.2% said smells hurt productivity. Khan's 2023 thesis found the detectors generalised poorly to more diverse documentation, with RoBERTa F1 falling to 0.71 to 0.93 after retraining, and practitioners rated fixing the Lazy smell as most feasible (snippet). The lesson is that rule-based detection is as good as ML on smells with a simple surface signature (length, redundancy with the signature) and much worse on smells that need semantic judgement.

### Detection techniques and reported performance

Rule-based and program-analysis tools came first. Wen et al. summarise the early line: iComment (NLP plus program analysis on lock and call rules), @tComment (Javadoc null and exception claims), and Fraco (rename refactorings), each targeting a narrow inconsistency class. They note one directive-checking tool reported about 80% precision over 1,146 defective directives and another outdated-comment detector about 75%, but these are reported second-hand in their related work.

Just-in-time (JIT) detection reframed the problem around a code change rather than a static snapshot. Panthaplackel, Li, Gligoric and Mooney (AAAI 2021) trained a model to decide whether a comment becomes inconsistent given a method edit, using 40,688 comment/method pairs from 1,518 Java projects covering @return, @param and summary comments (fetched, ar5iv). Their best JIT model reached precision 88.6, recall 72.4, F1 79.6; the best post hoc model (comment and code only, no diff) reached precision 62.6, recall 72.6, F1 67.2. The 12-point F1 gap between JIT and post hoc is the single most useful number in this literature for a drift tool: knowing what changed is worth far more than inspecting the current state. Their earlier ACL 2020 paper framed comment updating as predicting an edit sequence applied to the existing comment rather than regenerating it (fetched abs). Liu et al. (ASE 2021) named the task "just-in-time comment updating" and built CUP, a sequence-to-sequence updater; Lin et al. built HebCUP, a heuristic that beat CUP on single-token changes but not beyond; CUP2 (TSE 2023) pairs a detector with the updater (all snippet).

Learning-based post hoc detection improved with engineered features. CoCC (Huang et al. 2024) extracts features before and after a change on 49,648 code-comment pairs from 22 Java projects (16.8% positive) and reports precision 92.1%, recall 78.9%, F1 0.850 with random forest, and 89.4%, 75.7%, 0.820 on a 5,000-sample Python set (fetched HTML). Of its 15 most important factors, the top three are all distances between comment and code similarity before versus after the change, followed by proportion of changed lines, method invocation updates, variable declaration updates, method renaming, return type and parameter renaming. Steiner and Zhang (2022) framed the problem as natural language inference with BERT and Longformer but report no metrics on the abstract page (fetched abs).

LLM-based detection. DocChecker (2023) used a code LLM to detect and regenerate comments (snippet). CCISolver (Zhong et al. 2025) found "a substantial portion" of existing datasets mislabelled, released the cleaned CCIBench, and reports detection F1 of 89.54% plus a human-evaluated repair success rate of 0.6533 (fetched abs). Nguyen, Bui and Nguyen (SANER 2026, "Larger Is Not Always Better") fine-tuned CodeT5+ on ordered edit sequences (replace, delete, add) and report up to 13.54% higher F1 than prior models and 4.18% to 10.94% higher than fine-tuned DeepSeek-Coder, CodeLlama and Qwen2.5-Coder on JITDATA and CCIBench (fetched abs).

The most important LLM finding for this skill is DocPrism (Xu, Wahab, Holmes and Lemieux, ISSTA 2026, fetched HTML). Plain prompting of Llama 3.1-70B flagged 98% of functions as inconsistent, mostly because the model reports "under-promises" (undocumented code details) as inconsistencies. DocPrism separates incorrectness (over-promise: documented behaviour not implemented; direct mismatch: logical conflict) from incompleteness (under-promise) and filters the latter out in code after a per-category yes/no schema. The flag rate fell from 98% to 14% and F1 rose from 0.22 to 0.77 on the ablation set; on a broad evaluation across Python, TypeScript, C++ and Java the flag rate was 17% with precision 0.63 (0.66, 0.70, 0.56, 0.58 by language). On a real-world Java set DocPrism reached about 0.58 precision where the fine-tuned prior state of the art dropped to about 0.08, suggesting fine-tuned detectors overfit their benchmarks. Remaining false positives came from the model treating surrounding context as required behaviour.

Execution-grounded detection. METAMON (Lee, An and Yoo, 2025) generates regression tests to capture current behaviour, then asks an LLM whether generated oracles conflict with the documentation, reaching precision 0.72 and recall 0.48 on 9,482 pairs from Defects4J (fetched abs). CASCADE (Kiecker et al., FSE 2026) generates tests from the documentation, then also generates code from the documentation and only reports an inconsistency when the real code fails a test the doc-derived code passes, as a deliberate false-positive filter; it found 13 unknown inconsistencies across Java, C# and Rust, 10 fixed, but reports no precision on the abstract page (fetched abs). MPDetector (Xu et al. 2024) uses symbolic execution to extract multi-parameter constraints from code and an LLM to extract them from docs, with fuzzy comparison to absorb LLM variance; precision 92.8%, with 11 of 14 reported issues confirmed by maintainers (fetched abs). The pattern across all three is that high precision comes from grounding the comparison in something executable or formal rather than in two prose readings.

### README-level work

Prana, Treude, Thung, Atapattu and Lo (EMSE 2018) annotated 4,226 sections from 393 READMEs into What, Why, How, When, Who, References, Contribution and Other; What and How are common, purpose and status are often missing; a classifier reached F1 0.746 (fetched abs). Gao, Treude and Zahedi (2023, ICSE 2026 journal-first) analysed 1,163 README commits across 400 repositories that updated installation sections and found six change categories: pre-installation, installation, post-installation, help information, document presentation and external resource management (fetched abs). Gao, Lin, Treude, Gay and Zahedi (2026, "Does My README File Need To Be Updated?") is the closest paper to this skill (fetched HTML). On 25,511 PRs from 714 repositories they built a five-stage pipeline: C1 relevance classifier, C2 context-sufficiency judge, C3 patch retrieval, C4 paragraph localisation with justification, C5 a QA reviewer that rejects generic, hallucinated or unnecessary updates. Their best agentic configuration (Qwen-3-32B) reaches entry recall 0.50, specificity 0.99, index recall 0.68 and MRR 0.73, but only 28% "user-facing accuracy" because README updates accompany under 1% of PRs; a single-prompt baseline has recall 0.77 but specificity 0.70 and user-facing accuracy 0.03. Their failure analysis categories are context deficit, semantically irrelevant noise, document structural ambiguity and other, and they treat justifications that reference nonexistent files or sections as a hallucination signal. Manual annotation found 21.5% of "false positives" were updates developers had overlooked (6.1% conservatively).

## 2. Practitioner best practice

Docs as code. Write the Docs defines docs-as-code as producing documentation with the same tools and workflows as software: issue trackers, Git, plain-text markup, code review and automated tests; it notes teams can block feature merges that lack documentation (fetched). Google's engineering documentation guide (fetched) states the rules most relevant to drift: "a small set of fresh and accurate docs is better than a large assembly" in disrepair; "change your documentation in the same CL as the code change" and expect reviewers to check it; delete dead documentation, cleaning up gradually with "default to delete or leave behind if migrating"; link rather than duplicate; keep READMEs current with links to deeper docs; and turn design docs into archives once implemented rather than leaving them as half-correct guides. Google's style guide adds two rules that reduce drift at the source: "timeless documentation" avoids words such as currently, now, soon, new, latest, existing and "does not yet", because they date a page, while allowing them in release notes and other dated content (fetched); and "avoid documenting future features or products, even in innocuous ways" (fetched).

Freshness policies. The strongest published convention is to keep two dates. Cloudflare's docs show an automatic "Last updated" taken from git history and a separate "Reviewed" frontmatter property set only when someone has read the page from beginning to end (fetched). Metabase defines a documentation freshness metric as active items reviewed within their policy window divided by all active items, suggests 90 days for operational docs and longer windows for stable reference, and warns that "an automated edit is not proof of review" because bot edits, formatting and sync timestamps make stale guidance look fresh (fetched). Diátaxis does not prescribe a review cadence; its guidance is to improve iteratively, "choose, assess, decide, do", one paragraph at a time, and never to tear down and rewrite (fetched).

Docs CI gates. GitLab runs Vale with three tiers: errors (branding, trademarks, anything that breaks rendering) fail the job; warnings appear in the MR diff but do not fail; suggestions show only in editors (fetched). Vale itself is a Go binary that lints prose with YAML rules grouped into styles, parses markup so it can skip code blocks and link URLs, supports 12 markup formats and comments in 19 languages, and runs via a GitHub Action or pre-commit (fetched). A GitLab knowledge-graph MR shows the common three-tool split: markdownlint-cli2 for structure, Vale for prose, lychee for links (snippet). lychee checks Markdown, HTML, CSS, text and XML, verifies fragments with `--include-fragments`, caches results in `.lycheecache` with a one-day default age, takes `.lycheeignore` regexes, uses a GitHub token to avoid rate limits, and exits 2 when any non-excluded link fails (fetched README). A practitioner note on markdown-link-check reported running it weekly with `continue-on-error` because of flaky external links (snippet).

Executable documentation. Rustdoc extracts code blocks from doc comments and runs them under `cargo test --doc`; a block passes if it compiles and does not panic; `ignore`, `no_run`, `should_panic` and `compile_fail` attributes and hidden `#` lines keep examples honest without cluttering the rendered page, and the stated rationale is that "documentation that doesn't compile or gives wrong output is caught by the test suite" (fetched). `mdbook test` runs Rust blocks in book chapters through rustdoc, skipping `ignore` and non-Rust blocks (fetched). Python's Sybil parses ReST, Markdown and MyST, runs doctest and code-block examples as pytest or unittest tests, and supports skip directives (fetched). Elixir's `ExUnit.DocTest` turns `iex>` examples in `@doc` into tests and `doctest_file` runs examples from a Markdown file such as a README (fetched). Doc Detective goes further for procedural docs: it parses test steps embedded in markdown and executes them against a browser or API, checking element existence, text, screenshots, links and responses (snippet). For HTTP APIs, Dredd runs the examples in an OpenAPI document against the live server and Schemathesis adds property-based generation; a non-peer-reviewed benchmark on 30 specs reported 78% versus 91% contract coverage (snippet).

CLI help in sync with README. Several small tools replace a marked block in README with live `--help` output: readme-cli-help, update-markdown-usage, docsme for Cobra, and cli_readme_builder for Dart; cog runs Python inside marker comments and rewrites the output in place; embedme embeds source files into code blocks and has a `--verify` flag that fails CI if regenerating would change the file (snippet). The shared pattern is generate-then-diff: the doc contains a generated region, CI regenerates it and fails if the committed text differs.

Doc-to-code coupling. Swimm couples snippets, tokens and paths in docs to code; on every PR its Auto-sync algorithm updates routine changes (renamed variable, changed parameter value, moved path) automatically and flags "significant" changes, failing a verification check that can block the PR or open a time-boxed issue; users accept the auto-synced edits with an "Approve Auto-sync" button or by configuring automatic commits to the PR (fetched docs page plus snippet). stale-cli checks README and CONTRIBUTING against the code with configurable severities (missing file or dead command as error, undocumented env var as warning), posts PR comments, and has an optional AI mode off by default (snippet). A Dosu article describes a Claude Code GitHub Action run after merge to main that reads the diff and the docs, edits docs on a `docs/update-from-pr-N` branch and opens a follow-up PR; it relies on a CLAUDE.md table mapping code paths to the docs to check, skips internal refactors, bug fixes and performance work, offers a `skip-docs-check` label, and costs roughly 0.50 to 2.00 USD per run at 15 turns (fetched).

Academic systems that update docs. Lee, Heo and Dearstyne (ICSME 2025) fed code-change information to an LLM to update API docs and found the updates scored higher on METEOR than the outdated docs (0.771 or 0.776 versus 0.679 depending on the record), with a maximum F1 of 0.921 on code-related facts (snippet). Birru et al. (ENASE 2025) evaluated CodeDocSync with contextual relevancy, answer relevancy and faithfulness metrics in an industrial case (snippet).

## 3. Usable drift signals, ranked by cost and reliability

The ranking below combines the academic evidence (JIT beats post hoc by 12 F1 points; grounded checks reach 0.9 precision while prose-to-prose LLM judgement sits at 0.6; under-promises are the dominant false positive) with the practitioner tools above. Tier 1 signals are cheap and nearly deterministic; Tier 4 signals are expensive and need human confirmation.

Tier 1: deterministic resolution against the repository (cheap, high precision).
- Dangling file and directory references: a path in backticks, a relative link, or an image that does not exist in the tree. This is what lychee does for links and what Swimm's "smart paths" and stale-cli's "missing file" check do for prose paths. Wen et al. found obsolete references to other code elements as a recognised inconsistency type.
- Dangling symbols: a function, class, CLI subcommand, flag, config key, env var or npm/make/cargo script named in the doc that cannot be found in the code or manifests. stale-cli's "renamed npm script" and "dead command" examples are exactly this. Renames are the change type least likely to trigger a comment update (Wen et al.), so this signal catches the most common silent drift.
- Install instructions versus manifest: version constraints ("Node 16+") versus `engines`, `requires-python`, `rust-version`; package names versus `dependencies`; commands versus scripts in package.json, Makefile, justfile, pyproject. stale-cli's Node 16 example and Gao et al.'s installation-change taxonomy both point here.
- Generated regions whose regeneration differs: `--help` blocks, embedded source, API tables. Treat like embedme `--verify`.
- Broken anchors and intra-repo links, including headers referenced by other docs (lychee `--include-fragments`).

Tier 2: structural and version comparison (cheap, medium-high precision).
- Headers or tables that describe repository layout ("Project structure") compared with the actual tree. Deterministic to compare, but intentional elision (listing only important directories) is a benign mismatch, so report only missing or renamed entries, not unlisted ones.
- Badges and version numbers versus the manifest, tags and CI config: a version string in prose that no release matches, a badge pointing at a renamed workflow or a dropped CI provider.
- Config keys documented versus a schema (JSON Schema, pydantic model, clap or cobra definitions, env var reads). MPDetector reached 92.8% precision by extracting constraints from both sides and comparing them formally; a simpler key-set diff is lower effort and still deterministic.
- CLI flags documented versus flags defined. Same pattern, with the generate-then-diff tools as the mature form.

Tier 3: change-aware and temporal signals (cheap to compute, medium precision; raise priority rather than assert drift).
- Commit-date lag: the code paths a doc references have changed since the doc's last substantive commit. Metabase's warning applies in reverse: a formatting-only doc commit does not reset the clock, so measure against the last commit that touched the relevant paragraph, not the file. Wen et al.'s data say only 13% to 20% of code changes need a comment update, so lag alone is a prompt to look, not proof.
- Change type of the referenced code: signature, constructor, variable declaration and selection changes are the ones most likely to need a doc update; renames are the ones most likely to be missed (Wen et al.; CoCC's top factors include method invocation update, method renaming, return type and parameter renaming).
- Time-anchored words ("currently", "soon", "new", "does not yet", "will be") per Google's timeless-documentation list. These do not prove drift but they mark sentences with a short shelf life, and Google's future-features rule says they should rarely be in product docs at all.
- Doc-level freshness metadata (`reviewed:` frontmatter, "Last reviewed" lines) past its window, following Cloudflare and Metabase.

Tier 4: semantic and executable checks (expensive, precision 0.6 to 0.9 depending on grounding).
- Examples that would not run: extract fenced code blocks and run or at least parse them, in the spirit of rustdoc, Sybil and doctest_file; a parse error or an import of a missing module is near-certain drift, a runtime failure may be environmental.
- Behavioural claims versus code, judged by an LLM. Only reliable when restricted to incorrectness (over-promise and direct mismatch) with incompleteness filtered out, and when given the diff rather than a snapshot (DocPrism 0.63 precision at 17% flag rate; Panthaplackel JIT 88.6 precision). Grounding the claim in a test (METAMON, CASCADE) or a formal extraction (MPDetector) raises precision further but costs more.

## 4. What a good fix looks like

Rewrite only what resolved deterministically; flag everything else. The evidence for surgical edits over regeneration is consistent. Gao et al. (2026) list the costs of regenerating a README: it ignores existing content and style, drifts in style, hallucinates, costs a whole-codebase read, imposes a heavy review burden and does not show which change invalidated which part. Panthaplackel et al. (2020) model the update as an edit sequence on the existing comment for the same reason. Swimm's product line draws the boundary at mechanical changes (renamed identifier, changed parameter value, moved path) which it applies automatically, with everything "significant" flagged for a human. CCISolver's human-rated repair success of 0.6533 is the best published number for LLM comment repair, which means roughly one in three automatic rewrites of a semantic inconsistency would be wrong; that is acceptable for a proposal and unacceptable for an unattended commit.

Present changes as a reviewable diff with a justification per hunk. Gao et al.'s pipeline outputs a decision, a location and an explanation, and their QA stage rejects generic or hallucinated justifications; they found vague, hedged justifications were the signature of false positives. The Dosu workflow opens a follow-up PR listing each changed doc, the reason and the originating PR. GitHub's suggested-changes feature lets a reviewer attach a concrete edit that the author applies in one click, and several suggestions can be batched into one commit with co-author attribution (fetched); it is the natural shape for low-risk mechanical fixes. GitLab's Vale tiers give the policy template: errors block, warnings show in the diff, suggestions stay local.

Avoid hallucinating new content by construction, not by instruction. DocPrism found that telling the model not to report under-promises "helped only partly"; the flag rate only fell when the categories were enumerated as yes/no schema fields and the unwanted category was dropped in code afterwards. The same applies to fixes: constrain the fix to replace a resolved reference (old path to new path, old flag to new flag, old version to manifest version) or to delete a sentence, and require that every token introduced into a doc be traceable to a file, symbol or manifest value in the repository. Google's "delete dead documentation" and "default to delete" are the practitioner version: when a sentence describes code that no longer exists and there is no obvious replacement, the correct fix is usually deletion with a note, not invention. Gao et al.'s hallucination signal (a justification that cites a nonexistent file or section) should be an automatic reject in the fix stage too.

Handle intent versus implementation explicitly. The doc may be right and the code wrong. Google's docguide says method docs are "the contract for how code must behave" and documented behaviour should have a test. DocPrism's definition of incorrectness is symmetric: "either the code or the documentation is wrong". CASCADE operationalises the symmetry by generating code from the doc and only reporting when the real code fails a test the doc-derived code passes. A good tool therefore classifies each incorrectness finding as reference-level (a name or path that no longer resolves, which is almost always a doc fix) or behaviour-level (a described behaviour the code does not implement, which may be a bug) and never auto-fixes the second kind. The Gao et al. retrospective finding that 21.5% of apparent false positives were overlooked updates cuts the other way: a human reviewing a behaviour-level flag may decide the code needs fixing, so the flag should say "mismatch" rather than "doc is stale".

Keep the review loop small and iterative. Diátaxis recommends paragraph-scale assessment and immediate publication over big rewrites. Google says to clean up gradually, deleting what is clearly wrong first. The Dosu article reports that prompt tuning against reviewer corrections took a day or two and that each run starts without memory, so corrections must be encoded in a repo-level config (their CLAUDE.md mapping table), which doubles as the skill's allow-list and skip-list.

## 5. Known pitfalls and false positives

Incompleteness is not drift. DocPrism's 98% flag rate under naive prompting came from the model treating every undocumented code detail as an inconsistency. Docs are deliberately more abstract than code; the tool must never flag "the doc does not mention X" as staleness.

Intentional description of planned, deprecated or historical behaviour. Google's style guide bans future-feature documentation, but repositories still contain roadmaps, "Unreleased" changelog sections, deprecation notices and migration guides that describe old behaviour on purpose. Keep a Changelog defines the changelog as a chronological, curated record with an Unreleased section and "YANKED" markers; entries describe what was true at each version, so comparing them with current code is meaningless. Design documents are meant to become archives once implemented (Google docguide), and Metabase notes live runbooks and historical decision records should not share one freshness policy. Treat CHANGELOG, HISTORY, ADR and RFC folders, "Roadmap" and "Deprecated" sections and anything describing a version other than the current one as out of scope or as reference-only.

Generated and vendored content. Go's convention marks generated files with a line matching `^// Code generated .* DO NOT EDIT\.$` before the first non-comment text (fetched). Go's `vendor/` is regenerated by `go mod vendor` and must stay consistent with `modules.txt`, so editing it by hand is wrong by construction (fetched). GitHub Linguist's `.gitattributes` overrides `linguist-generated`, `linguist-vendored` and `linguist-documentation` are an explicit, machine-readable declaration a tool can read (fetched). Generated docs (API reference emitted by TypeDoc, sphinx-apidoc, rustdoc, clap-markdown, cog regions) should be regenerated, not edited; vendored docs and `node_modules`, `vendor`, `third_party`, `.venv`, `site-packages`, submodules and copied upstream READMEs describe someone else's code and must be skipped. The task statement's exclusion of superpowers plan and spec folders is the same category: those documents describe intended work, not current code.

Docs for other repositories or external packages. README sections about an upstream dependency, examples that import an external package, and links to other projects' docs reference symbols the local scan cannot resolve. Resolve symbol references only against the local tree plus declared dependencies, and treat an unresolvable name inside an example that imports an external module as unknown rather than dangling.

Licence files, contributor lists and templates. Wen et al. found copyright headers wrong for years, and the Apache Groovy case where a licence header lagged a real licence change by four years is a true drift example, but the fix is a legal decision, not a doc edit; flag only, never rewrite LICENSE, NOTICE or copyright lines. Template files with placeholders (`{{project_name}}`, `<your-org>`, `TODO`) in cookiecutter or scaffold directories reference nothing by design; detect placeholder syntax and skip. CONTRIBUTING and CODE_OF_CONDUCT are mostly process text and rarely reference code.

Flaky and rate-limited external checks. lychee's docs and the markdown-link-check practitioner note both show that external link checks fail transiently and hit GitHub API limits; run them with a cache, a token, retries and `.lycheeignore`, and never let an external 429 or timeout count as drift. Only local-file and intra-repo anchor failures are deterministic.

Date and churn traps. A formatting commit, a bot commit or a link-fix commit updates a doc's mtime without reviewing it (Metabase), so lag must be measured per paragraph against substantive changes. Conversely, Wen et al. show most code changes legitimately need no doc change, so lag without a resolvable reference is a prompt, not a finding.

Benchmark and label noise. CCISolver found a substantial share of existing CCI datasets mislabelled, Gao et al. note their ground truth is "what developers actually did, not ideal documentation", and Khan's detectors lost accuracy on new corpora. Any precision figure the skill reports about itself should come from a human-labelled sample on the target repository, not from these papers.

Structural ambiguity. Gao et al. list "document structural ambiguity" as a failure class: when a README has no clear section for the affected content, the localisation step guesses. Flag at file level with a quoted sentence rather than inventing a section.

## Design implications for a Claude Code skill

1. Treat the scan as change-aware by default: diff the code paths a doc references against the doc's last substantive commit, because JIT detection beat post hoc by 12 F1 points (Panthaplackel et al. 2021) and only 13% to 20% of code changes need a doc update (Wen et al. 2019).
2. Resolve every backticked path, link, symbol, command, flag, script name, env var and config key against the tree and manifests before any LLM judgement, since deterministic reference checks are the cheapest and most precise signal (stale-cli, Swimm smart paths, lychee, Wen et al. on obsolete references).
3. Separate findings into reference-level (name no longer resolves) and behaviour-level (described behaviour not implemented), and only ever auto-fix the first kind (DocPrism's symmetric definition of incorrectness; CASCADE; Google docguide on docs as contract).
4. Never report incompleteness: enumerate the inconsistency categories as explicit yes/no fields in the LLM output schema and drop under-promises in code, because prompt instructions alone did not stop a 98% flag rate (DocPrism).
5. Give the LLM the diff and the affected paragraph, not the whole README and whole codebase, following the C1 to C5 pipeline that reached 0.99 specificity versus 0.70 for a single prompt (Gao et al. 2026).
6. Produce surgical edits with one justification per hunk and reject justifications that cite files or sections that do not exist (Gao et al. 2026 QA stage; Panthaplackel et al. 2020 edit model).
7. Require every new token the fix introduces to be traceable to a repository artifact (a path, symbol, manifest value or `--help` output), and prefer deletion with a note when no replacement resolves (Google "delete dead documentation").
8. Tier the output like GitLab's Vale policy: dangling references and failed generated-region diffs are errors, date lag and time-anchored wording are warnings, style is a suggestion (GitLab Vale testing page).
9. Present fixes as a diff or PR for review, and for mechanical replacements use a shape that maps to GitHub suggested changes so a reviewer applies them in one click (GitHub docs; Dosu workflow).
10. Measure doc age per paragraph against substantive commits, excluding formatting, bot and link-fix commits, because "an automated edit is not proof of review" (Metabase; Cloudflare's separate Reviewed date).
11. Flag time-anchored words (currently, soon, now, new, does not yet) and future-tense feature claims as low-severity shelf-life warnings, per Google's timeless-documentation and future-features rules.
12. Try to parse or dry-run fenced code blocks and installation commands against the manifest before asking an LLM whether an example is stale (rustdoc, Sybil, ExUnit doctest_file, Dredd).
13. Skip or mark reference-only: CHANGELOG and release notes, Unreleased and Roadmap sections, ADR and RFC folders, design docs, LICENSE and copyright lines, templates with placeholders, and plan or spec folders (Keep a Changelog; Google docguide on archived design docs; Wen et al. on licence headers).
14. Honour machine-readable exclusions: `linguist-generated`, `linguist-vendored` and `linguist-documentation` in `.gitattributes`, `DO NOT EDIT` headers, `vendor/`, `node_modules`, submodules and cog or embedme marker regions, which should be regenerated rather than edited (Linguist, Go generate, Go vendoring, embedme).
15. Resolve symbols only against the local tree plus declared dependencies, and classify an unresolvable name inside an example that imports an external package as unknown, not dangling (DocPrism false-positive analysis on surrounding context).
16. Run external link checks with cache, token, retries and an ignore file, and never let a transient HTTP failure count as drift; only local path and anchor failures are deterministic (lychee README; markdown-link-check practitioner note).
17. Keep a repo-level mapping of code paths to the docs that describe them, plus skip rules and reviewer corrections, because each run starts without memory and the mapping is what stops the model guessing structure (Dosu workflow CLAUDE.md table).
18. Report "mismatch" rather than "doc is stale" for behaviour-level findings, since 21.5% of apparent false positives in the README study were updates developers had overlooked and some mismatches are code bugs (Gao et al. 2026; Google docguide).
19. Calibrate on a human-labelled sample of the target repo before trusting any self-reported precision, because published CCI datasets contain mislabelled data and detectors lose accuracy off-benchmark (CCISolver; Khan 2023 thesis; DocPrism cross-dataset results).
20. Weight findings by the kind of code change: signature, constructor, variable declaration and rename changes should raise priority, while literal, iteration and lambda changes rarely need doc updates (Wen et al. 2019; CoCC top factors).
