# document-drift: what this repository already provides

Research note for the `document-drift` skill design. Compiled 2026-10-09 from the state of `main` at `8439f5d`. It answers one question for the designer: what in `claude-skills` is already built, what rules a third skill must obey, and which primitives can be imported, copied or must be written fresh. Every rule and primitive carries a `file:line` citation to the checkout; where this note and the scripts disagree, the scripts win, which is the repository's own rule (`docs/architecture.md:7-9`).

Scope of the new skill, as briefed: walk a repository, find markdown documentation, compare it against the code, flag documents that are stale or that reference code which no longer exists, then fix them behind a human review gate. Superpowers spec and plan folders are excluded from the scan.

## 1. Conventions a new skill must follow

The repository holds two skills, `tech-debt-scan` and `karate-bootstrap`, and both were built under one fixed constraint list. The canonical statement is the opening of the v2 spec (`docs/superpowers/specs/2026-09-04-tech-debt-scan-v2-design.md:5`):

> Fixed constraints: Claude Code skill; SKILL.md orchestration with pinned commands, pinned output files and the exit-5 no-improvisation rule; pure Python 3.11+ with pyyaml as the only dependency, every script direct-path invocable as `python scripts/<name>.py`; read-only Agent subagents for all LLM work; language-agnostic by default, external tools only when already installed; human review of `design.md` before `promote.py`; no live LLM in tests; Windows-safe argv; LF-only rendered output; ruff, mypy strict, pytest and `skill_check.py` in CI.

The promote brainstorm spec inherits the same list verbatim (`docs/superpowers/specs/2026-09-10-tech-debt-promote-brainstorm-design.md:5`), which is the precedent for a new skill's spec: open with the inherited constraints, then a numbered guardrail list. Each rule below is quoted and cited.

**C1. SKILL.md frontmatter and triggers.** Both skills open with a YAML block carrying `name`, `description` and a `triggers` list (`skills/tech-debt-scan/SKILL.md:1-7`, `skills/karate-bootstrap/SKILL.md:1-6`). karate-bootstrap pins the shape in a test: `test_frontmatter_names_the_skill_and_its_trigger` asserts `data["triggers"] == ["/karate-bootstrap"]` and `test_description_carries_the_positive_terms_and_excludes_unit_tests` asserts the description is at most 1024 characters, contains every positive trigger term and states what the skill is not for (`skills/karate-bootstrap/tests/test_kb_skill_md.py:26-39`). The same file requires SKILL.md under 500 lines with ten `### Step N:` headings and a postcondition per step (`test_kb_skill_md.py:42-50`). The description convention is "Use when asked to ... Not for ..." (`karate-bootstrap/SKILL.md:3`); a document-drift description should name its triggers (stale docs, doc drift, docs out of date) and exclude what it is not for (code tech debt, which `tech-debt-scan` owns).

**C2. Scripts are direct-path invocable.** "Every script runs as `python scripts/<name>.py` from `skills/tech-debt-scan/`. No package install, no `-m`, no cross-module package layout (the only intra-`scripts` imports are flat top-level imports resolved by the test `conftest.py` and `mypy_path`)" (`docs/architecture.md:34-37`; also `README.md:42-43`, `SKILL.md:92-95`). The test side is `skills/tech-debt-scan/tests/conftest.py:7-14`, which inserts `scripts/` and `tests/helpers/` on `sys.path`; the type side is `mypy_path` in `pyproject.toml:43`.

**C3. Pure Python 3.11+, pyyaml only.** `requires-python = ">=3.11"` and `dependencies = ["pyyaml>=6.0"]` (`pyproject.toml:4-5`); "pip install pyyaml # the only runtime dependency" (`README.md:39`). Leaf modules go further and use the standard library alone, stated in their docstrings (`scripts/evidence.py:3`, `scripts/slugs.py:13`, `scripts/skill_check.py:19`, karate's `kb_check_skill.py:17`).

**C4. CI gates: ruff, mypy strict, skill_check, pytest, on 3.11 and 3.12.** `.github/workflows/test.yml:13-24` runs `ruff check .`, `mypy`, `python skills/tech-debt-scan/scripts/skill_check.py`, `python skills/karate-bootstrap/scripts/kb_check_skill.py` and `pytest -v`. Three `pyproject.toml` lists are per skill and must each gain a line for a third skill: `testpaths` (`pyproject.toml:16`), `[tool.mypy] files` (`:40`) and `mypy_path` (`:43`). `strict = true` (`:39`); ruff selects `E, F, I, B, UP, SIM` at line length 100 (`:29-35`) and excludes every `skills/*/tests/fixtures` tree as data (`:32`). `norecursedirs = ["fixtures/corpus"]` keeps pytest from collecting fixture `test_*.py` files (`:26`), which a drift corpus with planted test files will also need.

**C5. Language-agnostic rules.** Spec guardrail 0(d): "The only language-aware code is the inventory's extension map (which also supplies comment syntax) and the tool normalisers in `tools_probe.py`. Any per-language code path anywhere else is a defect" (`spec:12`). Enforced by `test_no_script_branches_on_a_language_name`, which greps every script under `scripts/` against `LANGUAGE_BRANCH_RE` and allows only `tools_probe.py` (`skills/tech-debt-scan/tests/test_patterns.py:744-753`; regex at `:453`). That test globs the tech-debt-scan scripts directory only, so a new skill needs its own copy of the test.

**C6. Redaction at every write.** "Every repository-derived string passes through `redaction.redact` at the point of writing, in every script" (`docs/architecture.md:39-40`), and "Where a string is also length-capped, `redact` runs first and the cap second" (`:48-51`). The phase 5b plan states it as a global constraint: "Redaction runs before any truncation at every capping site: `redact(text)[:n]`, never `[:n]` then `redact`" (`docs/superpowers/plans/2026-09-08-tech-debt-scan-v2-phase-5b.md:18`). The writer applies it to titles, proofs, quotes and free text (`scripts/design_writer.py:54-63`).

**C7. The `--workdir` artefact directory.** "`--workdir` (default `.tech-debt`) is the directory every chain script, from `inventory.py` through `design_writer.py render`, reads its inputs from and writes its outputs to. Pass the same `--workdir` to every command in one scan" (`SKILL.md:112-115`); "All intermediate artefacts live under `.tech-debt/` in the scanned repo ... The directory is gitignored" (`SKILL.md:86-87`). Spec 3.3: "Every v2 script accepts `--workdir` (default `.tech-debt`) and reads and writes the pinned file names inside it" (`spec:166`). `inventory.py`'s `DEFAULT_IGNORE` lists `.tech-debt` so a scan never reads its own workdir (`scripts/inventory.py:236`). A document-drift workdir (say `.document-drift/`) would have to be added to that ignore list if the two skills run on one repository, or document-drift must set it through the config `ignore` key (`scripts/config.py:34`).

**C8. Exit 5, no improvisation.** "If any expected output file from a numbered step is missing, abort with exit 5. Do not retry steps you weren't told to retry. Do not invent intermediate state. Do not skip steps" (`SKILL.md:53-55`). karate-bootstrap adds "Do not compose a subagent prompt yourself: render it with `kb_prompt.py`, and add nothing to the rendered text" and "Never push" (`karate-bootstrap/SKILL.md:21-28`), and names the code `EXIT_MISSING_OUTPUT: Final[int] = 5` (`skills/karate-bootstrap/scripts/kb_common.py:26`). Spec 3.3's failure posture: "A missing pinned output file after a numbered SKILL.md step is exit 5" (`spec:170`).

**C9. File paths between steps, never inline JSON.** "Large intermediate data (the inventory, leads, evidence spans) always passes between steps as a file path under `--workdir`, never inline JSON on an argv or hand-built into a prompt, a large inventory would blow the Windows 8191-char argv ceiling. `plan_scan.py` and `verify_prompts.py` render the scout and verifier prompts as files for the same reason; dispatch each Agent with the prompt file's content, not a hand-built one" (`SKILL.md:96-101`). Spec 3.3 measured the bound: "No file list ever appears on a command line; the longest expanded command ... is 299 characters" (`spec:166`).

**C10. Agents write their own output file and reply with a receipt.** Added by PR #21 after issue #19: "Agent output always comes back as a file the Agent wrote itself, never as a reply the driver transcribes. An Agent's reply is truncated at roughly 4 to 5 KB, and every artefact steps 6, 8 and 12 produce is larger (5 to 24 KB measured) ... Each dispatch names the output path; the Agent writes its JSON there with the Write tool (never a shell heredoc, which mangles JSON on Windows) and replies with a receipt only: the path, the byte count and the number of entries. The driver then checks that the file exists and parses" (`SKILL.md:102-111`; steps at `:151-156`, `:159-164`, `:177-181`; `docs/architecture.md:76-79`; commit `8439f5d`).

**C11. Windows argv limits and stdin prompts.** Beyond C9, the live harness documents the hard ceiling: "Windows caps a `CreateProcess` command line at 32,767 characters, and `list2cmdline`'s quote and backslash escaping pushes a quote-heavy verifier prompt past that ceiling" so "The prompt itself is piped to the child's stdin and is never an argument" (`docs/architecture.md:248-254`; `scripts/live_run.py:30-37`, `:164`, `:195-197`). Every subprocess call is a list argv, never a shell string (`architecture.md:242`; `scripts/git_history.py:12-13`).

**C12. No live LLM in tests.** Spec 0(e): "Tests feed canned JSON to scripts; the `live` pytest marker never runs in CI" (`spec:13`). `addopts = "-m 'not live and not maven and not containers'"` (`pyproject.toml:22`). "Tests never call a live Agent. Scout and verifier dispatch are exercised by feeding canned JSON to the scripts" (`docs/architecture.md:739-742`; `SKILL.md:251-252`; karate `SKILL.md:414-415`).

**C13. The evaluation log.** `docs/evaluation-log.md` is one table, "One row per live run ... Rows are appended, never edited, so a fixture can appear more than once" (`docs/evaluation-log.md:3`, `:17`), with the column list at `:188` and every change in what a row measures recorded as dated prose above the table (`:105-117`). `live_run.py` appends to it by default (`scripts/live_run.py:651`). The spec says what a bar is and how one is set or refused (`spec:787`). A document-drift skill that measures precision will need its own log or a second table in this one, since the columns are family-recall specific.

**C14. Where documents live and the superpowers workflow.** Specs are `docs/superpowers/specs/<date>-<topic>-design.md`, plans are `docs/superpowers/plans/<date>-<topic>-<phase>.md`, research notes are `docs/research/<topic>/NN-<name>.md` (directory listing above; this file follows it). Scratch brainstorm state under `.superpowers/` is gitignored (`.gitignore:13`), so only the finished spec and plan reach git. A spec opens with provenance and the inherited constraints, then "0. Guardrails": handoffs rendered with assumptions in three buckets, a confidence percentage per plan task, documentation shipped in the same PR as code, verify before commit, one branch and PR per phase (`spec:7-15`). A plan opens with the required sub-skill line, Goal, Architecture, Tech Stack, Spec reference, Global Constraints, Guardrails from memory with `[[tag]]` markers, and a per-task confidence table (`docs/superpowers/plans/2026-09-08-tech-debt-scan-v2-phase-5b.md:1-45`).

**C15. Documentation ships with code.** Spec 0(c): "`docs/architecture.md`, the repository `README.md` and `skills/tech-debt-scan/SKILL.md` are updated in the same PR as the code they describe" (`spec:11`); the plan guardrail "Keep documents in sync with every code change ... When a CLI flag is documented, read the argparse setup, never an existing example. [[keep-docs-in-sync]]" (`plan 5b:27`). This is, incidentally, the repository's own hand-enforced document-drift rule.

**C16. LF-only rendered output and pinned line endings.** `design.md` "is written LF-only (`write_bytes`) so it byte-matches across platforms regardless of `core.autocrlf`" (`docs/architecture.md:669-670`; `scripts/design_writer.py:40-41`). Goldens and corpus fixtures are pinned `text eol=lf` in `.gitattributes:1-8`. A drift skill that rewrites markdown must decide and pin its line-ending policy for the files it edits, which is a harder problem than rendering its own report, because the edited file's existing ending must be preserved.

**C17. Read-only agents for judgement.** "Scout agents use Explore semantics; they never write" (`architecture.md:38`); every scout prompt begins "you have read-only access (read and search files; change nothing). Do not invent findings, files, lines or quotes; every claim cites a file, a line range and a verbatim quote of at most 6 lines" (`scripts/categories.py:608-612`). karate-bootstrap's exception is explicit: the `generate` subagent is general-purpose and "may write files under `<tests>` only" (`karate-bootstrap/SKILL.md:89-93`). So an agent that writes is allowed when the SKILL.md table says where.

**C18. Human in the loop; the fix question.** tech-debt-scan: "Nothing is fixed automatically" (`README.md:11`, `:226`; `architecture.md:31-33`) and the spec's non-goals open with "Autonomous fixing" (`spec:31`); "Mow the lawn autonomy, applying fixes without review, is a separate follow-on, deferred and out of scope" (`README.md:287-288`). karate-bootstrap, by contrast, writes a suite, commits at phase gates on its own branch and never pushes (`karate-bootstrap/SKILL.md:13-15`, `:107`, `:392`), while forbidding edits to the application's own source (`:27-28`). document-drift's fix step edits the scanned repository's documents, which neither skill does today; the precedent for a writing step is karate's (dedicated branch, explicit `--no-commit`, never push), and the precedent for the review gate is tech-debt-scan's status round-trip (C21).

**C19. Every step names one command and one output.** "Every step names one command and one output. A step's postcondition is the file it must leave behind" (`karate-bootstrap/SKILL.md:66-67`), tested by `test_every_step_names_a_postcondition` (`test_kb_skill_md.py:50`). tech-debt-scan's steps follow the same shape with step numbers "fixed across phases" so a later phase inserts without renumbering (`SKILL.md:119-121`).

**C20. Exit-code tables.** karate-bootstrap publishes one (`SKILL.md:69-79`; constants at `kb_common.py:22-28`); tech-debt-scan documents `promote.py`'s 0, 2 and 6 and `inventory.py`'s 2 (`SKILL.md:256-269`). Exit 2 is "a gate or script rejected its input", 5 is the no-improvisation code, 6 is a partial-write code in both skills.

**C21. The status round-trip vocabulary.** `VALID_STATUSES` is `pending`, `approved`, `rejected`, `accepted`, `promoted` (`scripts/validation.py:7-9`), shared by the writer and the parser "so the write side and read side reject the same inputs" (`scripts/design_parser.py:40-41`). The user flips `status:` in `design.md`; promote reads it back (`README.md:63-66`).

**C22. `schema_version` on every JSON document.** `inventory.json` (`scripts/inventory.py:909`), `ranked.json` (`scripts/rank.py:32`), `baseline.json` (`scripts/baseline.py:42`), `candidates.json` (`scripts/merge_findings.py:84`), `verify-plan.json` (`scripts/verify_prompts.py:38`).

**C23. A root config file with printed defaults.** `.tech-debt.yaml` at the repository root supplies every threshold (`scripts/config.py:30-99`), and `python scripts/config.py <repo>` prints the effective values (`README.md:157-158`). `ignore` accepts plain names or globs (`scripts/inventory.py:373-385`).

**C24. Goldens change only through `UPDATE_GOLDENS=1`; canned agent replies never.** "Regenerate the deterministic goldens with UPDATE_GOLDENS=1 after an intentional change; never regenerate the scouts or verdicts by hand" (`tests/test_chain_goldens.py:3-6`; plan 5b global constraint at `:22`).

**C25. Pinned clocks in tests.** "Three clocks are pinned so the goldens stay stable" and "Every date a test compares is a pinned literal that is not the wall-clock date" (`tests/test_chain_goldens.py:14-20`; plan 5b `:21`). Staleness in days is a clock-derived value, so a drift skill's tests inherit this rule directly.

**C26. `skill_check` constraints on SKILL.md commands.** Every `python scripts/<name>.py` line is extracted and each `--flag` checked against the script's `--help` (`scripts/skill_check.py:9-17`, `:33`, `:94-100`). Two constraints follow: "any script with subcommands ... keeps every `choices=` option on a subparser, because the lint takes the first `{a,b}` group in the top-level help as the subcommand list", and "flag names stay distinct within a script, because flag matching is substring-based (`--top` is satisfied by `--top5`)" (`spec:654`). karate's copy tightened matching to whole tokens (`kb_check_skill.py:11-12`). CI invokes each skill's checker by path (`test.yml:22-23`), so a third skill is a third CI line.

**C27. Commit attribution.** "Commit messages end with `Co-Authored-By: Claude Fable 5.1 <noreply@anthropic.com>`" (plan 5b `:20`); the git log also carries a `Claude-Session:` trailer on every squash body (section 6).

## 2. Existing primitives, with a reuse verdict

Verdicts: **reuse as-is** (import it or copy the file unchanged), **copy and adapt** (the shape is right, the inputs or names are tech-debt specific), **not applicable** (solves a different problem; the pattern may still be worth borrowing).

**P1. The file walk.** `inventory.build_all(root, *, ignore=DEFAULT_IGNORE, churn_months=None, config=None) -> tuple[dict, dict]` (`scripts/inventory.py:783-946`) walks once via `_iter_files(root, names, globs)` (`:417-431`, sorted `rglob`, symlinks skipped, `.tech-debt.yaml` skipped) with `_is_ignored` (`:388-414`) applying `DEFAULT_IGNORE` (`:222-237`), the conditional `bin`/`build` rule (`:239-244`) and config globs. The size guard `_skips_read` never reads a file over 2 MB or with a NUL in its first KB (`:329-337`, `:252-253`). Verdict: **reuse as-is** for the walk and ignore logic, by importing or copying `_iter_files`, `_is_ignored`, `_ignore_sets` and the two ignore tuples. Limits that matter for drift: a file is a code entry only if its extension is in `EXT_TO_LANG` (`:810-814`); everything else is an artefact candidate matched by `ARTEFACT_CLASSES` name patterns (`:189-217`), and a file matching neither is dropped. `.md` is in the map (`:131`) but `.rst` and `.adoc` are not, so despite `PATH_CLASS_GLOBS["docs"]` naming them (`:182`) they never become docs-class entries and the docs block never sees them. `docs/superpowers/**` and `.superpowers/` are not ignored by default; the brief's exclusion must come through config `ignore` globs or a skill-level constant.

**P2. Path classification.** `_classify_path(rel, extra=None) -> str` (`:354-362`) over `PATH_CLASS_GLOBS` (`:170-183`) in `PATH_CLASS_ORDER` vendored, generated, tests, docs, else source (`:184`), matched with `fnmatchcase` against both the relative path and the basename. Verdict: **reuse as-is**. Limit: `test_*` matches a basename anywhere, so a `tests/README.md` is `tests` not `docs` (first match wins), which is the right answer for a drift scan that wants to skip fixture docs but needs stating.

**P3. `EXT_TO_LANG` and `LANG_COMMENT`.** The one language-aware table (`:111-132`) and the comment syntax per language (`:139-158`), with `markdown` carrying `<!-- -->` as its block comment (`:143`). Verdict: **reuse as-is**; the docs block already takes it as `code_exts=frozenset(EXT_TO_LANG)` (`:925`) so a doc reference "with a known code extension" is defined by this map.

**P4. The docs block.** `docs_signals.docs_block(entries, artefacts, texts, git_block, git_available, *, code_exts) -> dict` (`scripts/docs_signals.py:95-157`) returns `readme_present`, `readme_loc`, `contributing_present`, `adr_dir_present`, `changelog_present`, `changelog_last_commit`, `latest_tag`, `latest_tag_date`, `dangling_refs` and `stale_vs_code_days`. Reference extraction is two regexes, backtick spans and path-like tokens (`:47-48`); `_looks_like_ref` keeps a token only when it carries a code or config extension (`_EXTRA_DOC_REF_EXTS`, `:52-54`) or starts with an existing top-level directory, and drops URLs (`:79-85`); `_ref_exists` accepts an exact path, a source-stem match, any path ending in `/<token>` or starting with `<token>/` (`:88-92`). Staleness is `_doc_lag_days` (`:67-76`): whole calendar days the doc's `last_touched` lags the newest source file in the repository, floored at 0. Capped at `MAX_DANGLING_REFS = 200` (`:55`, `:132-135`). Tests at `tests/test_inventory_v2.py:884-942`. Verdict: **copy and adapt**; this is the seed of document-drift's deterministic stage, and it has five limits the brief cares about. It runs only over `path_class == "docs"` entries (`:120-122`), so only `.md` files (P1). Staleness is measured against the newest source file anywhere, not against the files the document references, which is what the gap analysis actually asked for ("compare the doc's last commit date with the newest among referenced files", `docs/research/tech-debt-scan-v2/04-gap-analysis-arch-test-docs.md:114`). A bare identifier (`issue_partial`, `pay.refund`) is not a reference unless it has an extension or a top-level-directory prefix, so symbol-level drift is invisible (`test_inventory_v2.py:928` pins `payments.killswitch` as not path-like). `_ref_exists`'s suffix rule means `utils.py` resolves if any `*/utils.py` exists. And the stop at 200 is silent.

**P5. Stem tokeniser and identifier tokens.** `reference_graph.file_stem(path) -> str` (basename before the first dot, lower-cased, `scripts/reference_graph.py:70-72`), `TOKEN_RE` (`:40`, keeps hyphenated names), `identifier_tokens(text) -> set[str]` (`:130-131`), `numbered_logical_lines` (`:94-114`, joins bracketed and comma continuations), `import_lines` (`:126-127`). Verdict: **reuse as-is** for "does the code still define a name the document mentions": intersect a doc's backtick tokens with `identifier_tokens` of the referenced file, which is one set operation per pair, the same trick the graph uses. `build_reference_graph(files, fan_in_cfg) -> GraphResult` (`:188-311`) is **not applicable**; it is file-to-file fan-in with an ambiguity rule, not doc-to-symbol.

**P6. Per-file git history.** `git_history.git_log_pass(root, months) -> list[Commit] | None` (`scripts/git_history.py:110-121`) runs one `git log --since --name-only --relative` with a record-separator format; `derive_file_history(commits, present, *, is_test, bot_authors, bulk_threshold) -> (dict[str, FileHistory], int)` (`:133-182`) yields `last_touched` as the first date seen per path (newest first, `:161-162`); `run_git` is a list argv with a 120-second timeout returning `None` on any failure (`:75-91`); `list_tags` (`:248-257`). Verdict: **reuse as-is** for last-touched and tags. Limits: there is no rename detection at all, no `-M`, `--follow` or `--name-status` anywhere in `git_history.py` or `inventory.py` (grep returns nothing), and a path "deleted before HEAD" is dropped on purpose (`:158-159`). document-drift's "the reference is dangling because the target was renamed" question (`categories.py:310`) therefore needs a new primitive, most likely one `git log --diff-filter=R --name-status -M` pass, built in the same list-argv, null-on-failure style. The window is months-bounded, so a document untouched for longer than the window has `last_touched` `None`, not an old date.

**P7. Redaction.** `redaction.redact(text) -> str` (`scripts/redaction.py:104-115`) runs `CREDENTIAL_RE` (`:46-50`) then `SECRET_TOKEN_RE` (`:52-78`), both cutting to `value[:4] + "***"`; `strip_url_userinfo` (`:89-96`) is a separate helper for URL fields. Verdict: **reuse as-is**, every write path. The module docstring explains why `CREDENTIAL_RE` is frozen (`:13-17`).

**P8. The design document writer and the status flip.** `design_writer.write_design(inputs, scan_date, out_path) -> None` (`scripts/design_writer.py:1168-1185`) renders in memory, self-checks by re-parsing (`:1133-1165`), then writes `design.md` LF-only and `findings.json`; `mark_promoted(path, slugs) -> None` (`:1203-1250`) flips `approved` to `promoted` in place, atomic `os.replace` via `.tmp`, previous content kept at `.bak`, idempotent on `promoted`. Document shape: literal YAML frontmatter, `# Top N` with one H2 per finding carrying a fenced `yaml` anchor, then H1 negative-space sections in `SECTION_ORDER` (`:101-109`). `free_text` escapes heading- and fence-shaped lines (`:414`), `heading_text` collapses a title to one line (`:456`), `_fence_for` wraps a quote in a fence one backtick longer than its longest run (`:641`). Verdict: **copy and adapt** the format and the helpers; **reuse as-is** `mark_promoted` if the drift document keeps the same anchor keys. The module itself cannot be imported for rendering: `load_inputs` demands six tech-debt documents (`REQUIRED_DOCUMENTS`, `:153`; `:194-235`) and it imports `tools_probe.TOOLS` (`:95`).

**P9. The parser.** `design_parser.parse_design(path) -> {"metadata", "findings"}` (`scripts/design_parser.py:223-295`) with `REQUIRED_KEYS = ("status", "slug", "severity", "category")` (`:56`) and `OPTIONAL_KEYS` (`:63-75`); a finding ends at the next H2 or H1, fence-aware with CommonMark length rules, unclosed fence is a parse error (`:16-36`). Verdict: **reuse as-is** provided the drift anchor carries those four required keys (`category` can be a fixed `doc-drift` or a drift kind). If the new skill wants extra anchor keys, `OPTIONAL_KEYS` is the one list to extend, and spec 4.11 shows that is the established pattern (`spec:578`).

**P10. Validators.** `validation.py`: `VALID_STATUSES` (`:7-9`), `validate_slug` with `^[a-z][a-z0-9-]{0,63}$` (`:51`, `:58-62`), `validate_status` (`:65-69`), `VALID_DEBT_TYPES` already containing `documentation` (`:17-33`). Verdict: **reuse as-is**. If document-drift wants a status beyond the five (say `applied`), that is a shared-vocabulary change; the cheaper reading is that `approved` means "apply the fix" and `promoted` means "fix applied", which maps onto the existing flow without touching the validator.

## 3. What `doc-drift` already detects, what is missing, and the seams

**What the scan does today.** The deterministic half is P4 and P20: dangling backtick or path-like references in `.md` files, whole-repository staleness in days, and presence flags for README, CONTRIBUTING, an ADR directory and a CHANGELOG against the latest tag (`spec:280`; family row at `spec:97`: "LLM scout, script lead", leads from `dangling_refs`, `stale_vs_code_days` and the presence flags, no tool probe candidates, "tier B until the live evaluation reports an F1"). The judgement half is one scout agent with the block at `categories.py:301-324`: "DOC DRIFT: documentation that contradicts the code it describes", questions "Cite both the document line and the contradicting code line", "Would the documented example still run as written?", "Is the reference dangling because the target moved, or was renamed?", "For an absence finding, aggregate per module rather than per file", and traps "A document that describes a planned or external interface is not drift" and "Generated API docs regenerate on release; check the generator, not the output". Findings are `debt_type: documentation`, `type_id: TD-08`, verified by the same three questions, and capped at tier B whatever corroborates them (`apply_verdicts.py:126-127`).

What that yields in practice is in the golden: on `service-py` the scout returned three findings, each citing the doc line and the code line, for the README's claim that `src/pay/exporter.py` was removed while `legacy_export.py` still ships, the `python -m pay.refund --help` instruction against a module with no CLI, and a CHANGELOG with no entry for the `0.2.0` in `pyproject.toml` (`tests/golden/service-py/scouts/doc-drift.json`). The planted README defect is `README.md:10` (`tests/fixtures/corpus/service-py/files/README.md:9-10`; `planted.json` `p20`, `expect_tier: B`) and `doc-drift` recall reads `1.00` on every `service-py` row of the log (`docs/evaluation-log.md:190-205`). `web-ts` and `mixed-decoys` plant no doc-drift item and no doc-drift decoy at all (`planted.json` counts 0), so the family has one positive case and zero decoys in the corpus.

**What the gap analysis said was missing.** TD-08's verdict was "PARTIAL, drift covered and absence not" with a nine-row symptom table (`docs/research/tech-debt-scan-v2/04-gap-analysis-arch-test-docs.md:95-107`): absent or stub README, public symbols without doc comments, CHANGELOG behind tags, no ADRs or contributing guide, and "docs untouched while referenced code churned" were all unsearched in v1. The v2 docs block closed the presence flags and the whole-repo staleness; it did not close per-reference staleness ("compare the doc's last commit date with the newest among referenced files", `:114`), the public-symbol ratio ("needs a parser per language; a regex approximation is low precision, so report per module or mark not assessed", `:115`), or rename-aware dangling detection. The risk paragraph is the one a drift designer should quote back: "Missing docstrings are diffuse and individually trivial; one finding per undocumented function would flood the list. Aggregate per module and keep the absence of ADRs at severity 2 or below on its own" (`:120`). The consolidated taxonomy row lists the full symptom set and the headline numbers ("Of 101 doc defects: 35 missing, 23 wrong examples, 19 outdated", `02-debt-types-consolidated.md:36`). The agent-skill survey records that the most-adopted pure-Claude skill treats "documentation drift" as one of nine categories and tags re-runs RESOLVED and NEW against the prior report (`03-survey-agent-skills.md:43`), and lists baselines and diffing among what "the best designs add" (`:124`).

So the delta a standalone `document-drift` skill owns, none of which tech-debt-scan does: per-document, per-reference staleness against the referenced files' own history; rename detection; symbol-level references (a backtick `issue_partial` against `identifier_tokens` of the referenced module); commands and flags in fenced blocks checked against the scripts they invoke (the repository's own `skill_check.py` is a worked example of exactly this check, limited to `python scripts/*.py` lines); `.rst` and `.adoc`; and, above all, the fix. tech-debt-scan explicitly will not fix (C18).

**Three integration shapes.**

(a) *Standalone.* Own `SKILL.md`, own workdir, own report document in the same anchor format, own baseline, own fixture corpus. Reuses P1 to P7, P9 to P12, P21 to P27 and copies P8, P13 to P16. This is the shape the brief describes and the one the current repository layout supports without touching tech-debt-scan.

(b) *Promoted from a tech-debt-scan finding.* `/tech-debt-promote` step 6 writes `.tech-debt/evidence.md` for one approved finding and step 7 reads it and invokes `superpowers:brainstorming` (`SKILL.md:213-224`). `evidence.md`'s metadata line carries `Finding: <fingerprint> | <family> | <type_id> | <debt_type>` (`evidence_doc.py:99-101`) and its `### Evidence` bullets are the three citation shapes `evidence_locations` parses (`:35-37`). The seam is one branch in promote step 7: when `family` is `doc-drift`, hand `evidence.md` to `/document-drift --from-evidence <path>` instead of the brainstorm, and let document-drift's fix gate take over. Nothing in the scripts needs to change for that; it is a SKILL.md instruction plus a flag on the new skill that parses the metadata line and the evidence bullets with the regex at `evidence_doc.py:35-37`. The spec's rule that the brainstorm "always ends by invoking `superpowers:writing-plans`" (`SKILL.md:225-228`) would then be waived for this family, which is a spec amendment to record.

(c) *Both, with a feedback edge.* A deterministic document-drift checker could also register as an external tool in `tools_probe.py`'s registry so tech-debt-scan's doc-drift scout receives its signals as `tool` leads and `tool:document-drift` corroboration (`docs/architecture.md:270-276`, `:309-313`). Two facts limit this: the registry "never installs anything" and detects presence by `shutil.which` (`:293-300`), so document-drift would have to be on PATH as a command; and the doc-drift cap never lifts on a `tool:` token (`apply_verdicts.py:79-80`), so the corroboration would raise nothing above B until that cap is amended. (c) is therefore a later phase, not a design input.

## 4. The determinism split, as this repository states it

The principle: "**LLM does the judgement, scripts do the determinism.** The model runs each dispatched family's scout, verifies a batch of candidates against that family's questions and traps, and writes one remediation note per top-N finding; `rank.py`'s fixed formula deterministically scores every verified finding and picks the top N, no agent chooses or orders the final list. File walking, prompt rendering, markdown rendering, parsing, validation, and evidence-document rendering are all pure Python with pinned commands and pinned output files, no improvisation" (`docs/architecture.md:22-30`; the same split at `README.md:11-16` and `SKILL.md:21-27`). karate-bootstrap's statement of it: "Scripts do every deterministic step (discovery, the ledger, gates, scaffolding, report parsing, git checkpoints); you do the judgement inside narrow subagent tasks (tracing code paths, confirming validation rules, writing features) and the fix loop" (`karate-bootstrap/SKILL.md:13-15`).

Concretely, in the fifteen-step scan (`SKILL.md:123-189`) the scripted steps are 1 (`inventory.py`), 1a (`concern_index.py`), 2 (`patterns.py`), 3 (`rules.py`), 4 (`tools_probe.py`), 5 (`plan_scan.py`, which renders every scout prompt to a file), 7 (`merge_findings.py`, which re-finds every quote on disk and diverts a finding whose quote is absent, `spec:26`), 8's first half (`verify_prompts.py`, selection and prompt rendering), 9 (`apply_verdicts.py`, the tier table), 10 (`rank.py`), 11 (`baseline.py diff`), 12's first half (`design_writer.py notes-prompt`) and 13 (`design_writer.py render`, self-checked through `design_parser.py`). The agentic steps are exactly three: 6 (one read-only scout per plan entry), 8's second half (one read-only verifier per batch) and 12's second half (one read-only note agent). On promote, steps 3, 4 and 6 are scripts (`promote.py`, `baseline.record`, `evidence_doc`) and steps 7 and 8 are the brainstorm and planning skills (`SKILL.md:193-228`). Two further rules shape the split: a scout never self-reports confidence ("tiering is the verifier's job, not the scout's", `categories.py:13-14`), and a scout never proposes a fix (`:538`).

By analogy, a document-drift split argues itself: scripted are the doc walk and classification, reference and symbol extraction, existence and rename checks, per-reference last-touched, fingerprinting and quote relocation, prompt rendering, verdict application, report rendering and parsing, the status round-trip, the baseline diff, and the mechanical application of an approved edit (a `.tmp` + `os.replace` + `.bak` write, P27). Agentic are the reading of a documented claim against the code it describes (is the example still runnable, does the prose contradict the signature), the verification of a candidate with the three-file exploration allowance, and the authoring of replacement text. Whether the fix text is authored before or after human approval is the one new design decision; the repository's precedent (the note agent writes remediation prose before the human reads `design.md`, `SKILL.md:177-181`) suggests proposing the edit in the report so the human approves a concrete diff, and applying it by script afterwards.

## 5. Test and evaluation conventions, and what a drift corpus needs

**Fixture corpus.** `tests/fixtures/corpus/<name>/` holds `files/` (the final tree), `history.yaml` (an ordered commit list with author, date, subject and per-file content, plus optional `branch`, `delete` and `tag`) and `planted.json` (`spec:660-668`; `make_history.py:3-8`). The replayed tree must equal `files/` byte for byte (`test_replayed_tree_equals_files_dir`, plan 5b `:23`), and new files go in a new trailing commit so earlier hashes do not move (`history.yaml:1-6`). `planted.json` carries a top-level `churn_months` (240) because fixture dates are fixed while the default window moves (`docs/architecture.md:747-753`), `planted[]` entries of `id`, `family`, `type_id`, `path`, `lines`, `expect_tier`, and `decoys[]` of `id`, `family`, `path`, `why`, `sources` and an optional `lines` range when a decoy shares a file with a planted item (`service-py/planted.json`; `docs/evaluation-log.md:179-182`). Every decoy must carry a non-empty `sources` list (`spec:670`; `test_every_decoy_names_its_sources`, `architecture.md:187-188`). Multi-language requirement: three fixtures, Python, TypeScript and Go, "every pattern rule has a positive case in at least two of them" (`spec:670`).

**Goldens.** Per fixture: canned `scouts/<family>.json` and `verdicts/verify-<nn>.json` (real agent output from the first live runs, never regenerated), hand-written `notes.json`, and deterministic `candidates.json`, `verify-plan.json`, `verified.json`, `ranked.json`, `diff.json`, `design.md`, `findings.json` compared byte for byte and regenerated only under `UPDATE_GOLDENS=1` (`tests/golden/` tree; `test_chain_goldens.py:1-12`). One finding per fixture is hand-added with a quote not in the file so the diversion path runs every time (`:22-26`). The e2e test drives scan, a user edit, promote, and the scan-decide-rescan baseline sequence with no mocking (`tests/test_e2e.py:1-9`).

**Decoys as a design tool.** The corpus decoys are the repository's statement of what looks like debt but is not: fixture duplication under `tests/`, placeholder credentials, a pinned `requirements.txt` with no lockfile ecosystem, a package `__init__` with unresolved fan-in, a harness file run by name, a ticketed TODO, a bounded enum loop, an adapter pattern (`service-py/planted.json` decoys `d1` to `d10`). The 2026-09-09 run shows why they matter: a single decoy at tier A blocked setting the precision bar (`docs/evaluation-log.md:119-141`).

**Live evaluation.** `live_run.py` replays a fixture, runs every stage with real agents under a budget, scores `findings.json` and appends one log row; it refuses to score a workdir holding a `diff.json` or `baseline.json` "since scoring there would set a bar from a filtered population" (`README.md:181-214`; `architecture.md:190-240`). Run documents are kept under `docs/research/tech-debt-scan-v2/runs/<date>-<phase>/<fixture>/` (`spec:680`).

**By analogy, a document-drift corpus** needs at least one fixture with real git history, because staleness and rename detection are history facts. Planted drift, each with the file and line of the doc claim: a backtick path to a deleted file; a path to a file renamed in a later commit (the `history.yaml` `delete` plus a new path in one commit gives the rename, since `make_history` has no rename key); a bare identifier the code no longer defines; a command in a fenced block with a flag the script no longer accepts (`skill_check` is the oracle shape); a documented example that imports a symbol that moved; a CHANGELOG behind a `tag`; an ADR describing a layering the imports contradict; a README section untouched while its referenced file churned through several commits. Planted decoys, each with `why` and `sources`: a path that resolves only as a directory (`test_inventory_v2.py:925` already pins `src/cart`); a dotted name that is prose, not a path (`:928`); a URL; a reference inside a fenced block that is illustrative pseudo-code; a document that describes a planned or external interface (the family's own trap, `categories.py:314`); a generated API document (`:315`); a document newer than the code it describes (`test_inventory_v2.py:902-920` pins zero days); a README under `tests/fixtures/` that is fixture content; anything under `docs/superpowers/` or `.superpowers/`, which must be skipped rather than scored. A new golden kind has no precedent: the expected patched document after an approved fix, compared byte for byte with the line endings of the original preserved. The log needs its own columns (per drift kind precision and recall, decoys fixed, fixes applied over fixes approved).

## 7. Sharing code between the two skills today, and the options for a third

The repository does not share any code between `tech-debt-scan` and `karate-bootstrap`. A grep for `tech-debt`, `redaction` or `inventory` in `skills/karate-bootstrap/scripts/` returns nothing, and `karate` appears nowhere in `skills/tech-debt-scan/scripts/`. Where the second skill needed something the first had, it copied and renamed: `kb_check_skill.py` is `skill_check.py` with whole-token matching (`kb_check_skill.py:1-18`), `kb_common.DEFAULT_IGNORE` is its own list (`kb_common.py:32-49`), and karate carries its own `conftest.py`, helpers and dry-run harness (`tests/test_kb_dry_run.py:1-12`). The README installs each skill by symlinking its directory into `~/.claude/skills/` separately (`README.md:20-34`, `:88-94`), so at install time a skill directory must be self-contained; a flat `from redaction import redact` inside `skills/document-drift/scripts/` resolves only if `redaction.py` sits in that same directory.

The options, given C2's flat-import rule and the symlink install:

- *Copy the files.* The repository's actual precedent. Costs drift between copies (the very defect the new skill hunts), so a test that asserts the copy is byte-identical to the original, or a note in each copy naming its source, is the minimum.
- *A shared package under `skills/_shared/` or `lib/`.* Breaks C2 ("no cross-module package layout") and the per-directory symlink install unless each skill's `scripts/` adds the shared path to `sys.path` at import time, which the spec's "direct-path invocable" rule currently forbids.
- *Symlinks inside `skills/document-drift/scripts/` to the tech-debt-scan files.* Works on the checkout and keeps one source of truth, but git symlinks on Windows need developer mode or admin (`README.md:28-29` already warns about this for the install symlink), `_iter_files` skips symlinks (`inventory.py:423`), and ruff and mypy would lint the target twice.

The pragmatic reading is the first option with a byte-equality guard, which is what the repository did once already, and a later consolidation if a third copy appears. Which files to copy is section 2's "reuse as-is" set: `redaction.py`, `validation.py`, `slugs.py`, `evidence.py`, `design_parser.py`, `git_history.py`, `reference_graph.py` (for `file_stem` and `identifier_tokens`), `skill_check.py`, the walk and classification parts of `inventory.py`, and `tests/helpers/make_history.py`.
